## 1. 目标与范围

将合入主干前的完整回归单位从每个实现 PR 改为一个有界业务批次。子 PR 保持可审查，批次最终候选完成 full 后才可进入 main；本地不重复执行已有可信、适用证据覆盖的验证。第一阶段保留批次合入后的 main full，先验证批次路由、修复与主干准入；第二阶段通过独立验收后才允许 main 复用同代码树证据。失败修复或候选变化仍须重新验证，不承诺每批永远只运行一次。

这是验收证据与合入次序的设计变化，按 T2 处理。范围仅包括项目工程规则、验证路由、CI、回归测试及 GitHub 分支保护；不改变业务契约、测试断言、持久化用例库存或人工验收。无需通用任务调度器、自动 Agent 启动或第二份工作流状态文件。

相关权威为 [验证基准 §2.1.1](../high-level-docs/08-verification-baseline.md#211-配置化验证目标与-ci-路由)、根 AGENTS.md 和 `.vibe/project.yaml`。批准实施时同步修改这些规则；本提案不将旧代码与新 MVP 自动归为互不影响。

## 2. 批次与分支

每批通常从已完整验证的 main 基线建立一个同仓库、短期存在的 `batch/<goal>` 分支，围绕一个可验证结果组织工作，不建设长期积累的公共集成分支。批次可以只有一个 PR；2–4 个相关子 PR 仅为初始规模建议，不为凑数量拆任务或等待。按目标可验证、依赖已满足且累计改变仍可审查来收口；无依赖的业务目标分别成批。第一阶段同一时刻只协调一个批次的最终验证与合入，其他批次仍可开发；main 更新后，后续收口批次重新同步基线。

普通业务实现、业务修复和 UI 实现的子 PR，其 base 统一为所属批次分支；紧急修复采用单 PR 批次并优先处理，不降低主干入口验证。子 PR 可以完成审查并在获授权后合入批次，但此时仅表示“已集成、待整批验收”，不标记产品交付、不关闭依赖整体验收的 Issue。仅以阶段工程结果为验收的子任务，可在其验收满足且获授权后关闭；批次完整用户目标仍保持待验收。批次 PR 的 base 必须为 main，累计包含该批的全部改变。

直接面向 main 只保留两类窄例外：完整 diff 满足现有严格文档条件的独立文档 PR；以及 §5 中为启用本流程而明确列出的工程引导 PR，后者继续旧 full 门禁。启用后常规工程门禁变更也进入批次，并保留子 PR full。普通业务 PR 不因现有低风险 UI allowlist、紧急标签或单 PR 规模而绕过批次；外部 fork 的业务改动也必须先纳入同仓库批次。批次 PR 即使最终只剩文档，也不使用直接文档例外。

积累期间不创建批次 PR，避免每次子 PR 合入就触发 full。收口时创建批次 PR，冻结增加新功能，只接受当前批次缺陷修复、必要文档及基线同步；之后每次修改都会使此前最终版本证据失效。main 变化时先更新批次基线并重新验证。已有直接面向 main 的业务 PR 不自动迁移；实施切换前明确迁移范围并重新核对验收要求，未迁移的业务 PR 在新模式下不得以旧路由进入 main。

批次分支保持基本可构建、可测试。子 PR 的阶段检查与批准覆盖实际当前 base/head 和合并候选；批次基线更新后重新检查适用性，不将旧组合的绿灯视为当前组合已验证。批次分支的 PR 准入落实对应阶段必需检查，限制直接推送与绕过；意外发现基础构建或当前阶段测试失败时，暂停接收依赖该失败路径的新功能并先修复，不等待整批 full 才处理已知缺陷。

## 3. 验证与审查矩阵

| 场景 | 本地与 CI 要求 | 完成含义 |
| --- | --- | --- |
| 严格文档子 PR | `docs` | 文档检查通过 |
| 同仓库、base 为合法批次分支的普通实现子 PR | `code`、任务 Verify 明确的针对性行为检查及独立审查 | 可进入该批次；完整持久化及集成验收待批次完成 |
| 验证规则、CI、依赖、构建配置或测试收集/执行工具改变 | 仍进入批次，子 PR 保持 full；仅 §5 工程引导 PR 可直接面向 main | 避免由变更自身取消必需验证 |
| 批次 PR → main | 始终 `full`，检查完整累计 diff，独立复核最终版本与子 PR 审查结论 | 可进入主干合入门禁 |
| 严格文档 PR 直接 → main | `docs` 与适用审查；累计 diff 必须满足严格文档条件 | 仅文档例外，不证明业务完整验收 |
| 普通业务 PR 直接 → main | `main-admission` 拒绝；改入所属批次后重新验证和审查 | 旧 code 或后来通过的 full 均不自动豁免目标分支要求 |
| 外部 fork、未知 base/事件、无法建立 diff 或不满足批次条件 | 不获轻量降级，验证回退 full；准入资格另行判断，未知资格不得进入 main | 回退 full 不是批次入口豁免 |
| 第一阶段批次合入后的 main push | 始终 full，包括只有文档或 UI 的批次 | 保留合入后独立验证，不启用同 tree 复用 |
| 第一阶段其他 main push | 严格文档独立交付保持 docs，其余 full | 不追认未经准入的写入合法 |
| 第二阶段批次合入后的 main push | 仅在第二阶段启用后核验完整证据；满足全部条件可复用，否则 full | 明确实际合并版本与来源验证的对应关系 |

不以 Draft、标签、提交说明、文件命名猜测或测试结果缺失触发降级。批次资格由真实 PR 事件的 base/head repository 与 base 分支判定；异常、未知事件和无法建立变更范围继续 full。批次 PR 优先于 docs/UI 路由，防止整批被最后一次文档修订降级。

PR 改 base 必须重新路由，监听 `edited` 并处理其中的 base 变化。main 使用专用 `main-admission` 检查，分别判断入口资格和必需验证：业务交付须来自合法批次，严格文档或工程引导例外须独立证明其范围。子 PR 的 code 成功不能产生这个准入证明；不能通过一个在子 PR 上 skipped 的同名 job 伪造成功。首版可使用仅针对 main PR 触发的独立准入工作流，核验真实 base/head、累计 diff、阶段所需 target 和结果。合入前再次核对当前边界；子 PR 从 batch 改为 main，不能沿用原批准或绿灯，即使 head 未变也不能成为普通业务直达路径。

本地也采用同一交付阶段要求：普通批次子任务不要求先在本地 full 再推送。批次收口优先使用最终候选的可信 CI；本地按问题做聚焦诊断，不重复执行已有当前候选可信证据覆盖的 full。第一阶段不以模型判断的同 tree 为由跨修订复用证据。具体 Issue/设计已有更严格要求时，在采用批次前明确将完整验收绑定到批次出口，不能静默覆盖。

Planner 在子任务 Verify 中明确本次行为风险对应的确定性检查，例如 RLS 改变的越权拒绝、事务改变的回滚或并发行为；需成为强制门禁的检查必须具有已配置、可执行的验证路径。范围外的完整持久化回归可延期至批次出口，但本任务约定的检查失败不能延期消化或交接为 PASS。第一阶段不建设自动用例依赖分析，也不将针对性检查默认扩大为每个业务子 PR 的 full。

`code` 仍是现有格式、lint、类型、普通测试、Workspace 构建/浏览器、架构和契约检查，不等于瞬时检查。第一版不增加自动选择受影响数据库用例的依赖分析系统。子 PR 的数据库问题可能延迟到批次收口才发现，这是批量方案明确接受的取舍；批次失败时停止进入 main，修复仍留在同一批次。

子 PR 审查只批准进入批次，明确记录缺少整批 full 的边界。批次最终审查检查累计影响、冲突解决、新旧依赖组合与每条验收标准的归属。必须保留现有 `.vibe/reviews/pr-<number>/Review.md`，以及所需人类技术审查；独立审查可以复用子 PR 的语义分析，但不能将旧 SHA 的批准直接提升为新 SHA 的批准。

## 4. 批次收口、失败处理与验证证据

### 4.1 第一阶段：固定候选与主干验证

批次 full 在包含当前 main 的最终合并候选代码上执行，记录 PR 编号、base SHA、head SHA、实际 checkout SHA、Git tree、workflow 身份、run id、attempt 和全部选定任务结果。检查实际 checkout 与声明候选一致。三个持久化分片必须全部成功，缺失、失败、取消和意外跳过均拒绝。

平台依据：GitHub 的 [pull_request 事件](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request)区分 PR head 与模拟合并提交；[必需状态检查](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)必须对应当前提交；[严格分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-status-checks-before-merging)要求与 base 保持同步。实施时使用这些真实平台语义，不将 head SHA 与 checkout SHA 混记。

合入前复核 head/base 未变、候选结果仍成功、最终审查及人工门禁满足；任何基线变化、解决冲突或新增提交都重新 full。合并操作必须生成与测试候选相同的完整代码树，不能沿用一个没有包含最新 main 的 head 测试。

第一阶段批次最终合入使用普通 merge commit，并保留合入后 main full；不得用拟议的第二阶段规则跳过。合入前已完成 full 是主干准入条件，合入后的 full 不是未验证代码先进入 main 的补救许可。main full 未成功前不宣布该批次验证收口、不启动下一批次最终合入或依赖此结果的发布；失败按 §4.2 恢复。

核验任务只申请实际需要的只读权限。第一阶段通过当前 workflow 的依赖结果汇总验证，只读取 PR/commit 元数据，使用 `pull-requests: read` 和 `contents: read`；后续若读取 Actions 运行 API 才增加 `actions: read`。等待 CI 仍由原执行会话绑定确切 run/attempt/SHA 的外部 waiter 负责，收到完成事件后继续授权范围内的修复或交付；不创建新会话等待、不由模型循环查询。

### 4.2 批次失败与修复

批次 full 或最终审查发现阻塞时，保留当前失败证据，停止进入 main，并维持冻结。由原执行上下文协调 Implementer 修复与独立 Reviewer 复核，无需第四个角色或每个失败各建一个工作流账本。批次目标、现有设计及用户授权范围内的集成修复继续执行；新语义、范围扩展或实际缺少授权分别走既有处理规则，不能因“修 CI”获得额外权限。

| 失败类别 | 处理与恢复条件 |
| --- | --- |
| 本批代码缺陷、跨子任务契约或状态不兼容 | 留在同批修复，先聚焦复现；Reviewer 检查修复及受影响的原结论，新候选重新 full |
| CI 配置、测试收集、验证工具或断言本身有误 | 以权威要求判断测试是否有误，审查验证机制的变更；不能取消必需检查、减少覆盖或放宽正确断言换取通过；新候选重新 full |
| 网络、runner、镜像服务等外部失败 | 与代码缺陷区分，按环境恢复规则做窄探测和有界重试；必需验证仍记未完成，超出重试预算后报告阻塞 |
| 新的业务、契约或设计决定 | 返回 Planner 解决决定，暂停依赖它的修复；不静默改变验收或业务语义 |
| 需要移出、撤回或替换某个子任务 | Planner 重新确认批次目标及剩余依赖，按授权调整；保留原记录，新组合重新审查与 full，不能复用移除前的批准 |

修复通过补丁 PR 进入同一批次，执行其阶段检查和独立审查；保持批次 PR 冻结新功能。每个新候选都重新完成 full，不能将多个不同 SHA 的成功分片拼成一次通过。未改代码的外部瞬时故障也先按第一阶段的简单策略重跑完整 workflow；首版不实现跨 attempt 拼装部分成功证据，重试次数按既有有界恢复规则控制。取消、超时和 waiter 的 monitor error 均不是 CI 通过，后者也不直接证明代码失败。

第一阶段若 main 合入后 full 失败，暂停后续批次最终合入和依赖该结果的发布，先区分代码、验证机制与环境原因。无代码变化时按上述有界恢复重试；需要代码修复时允许以故障 main 建立明确标注的单 PR 恢复批次，记录故障修订及最近已验证基线，不谎称起点已通过 full。这是普通批次起点规则的窄恢复例外，不允许业务扩展；恢复候选仍在合入前 full 和独立审查，合入后 main full 成功才恢复正常收口。撤销已合入内容或回滚仍按明确授权执行，不自动重写 main 历史。

### 4.3 Review 文档与最终确认

每个子 PR 和批次 PR 继续保留所需 `.vibe/reviews/pr-<number>/Review.md`，在相应 PR 关闭前提交；不以 PR 评论替代正式审查文档。该文档承载语义审查与发现处理，GitHub PR/review 承载固定候选的最终确认，两者共同构成审查证据；第一阶段项目规则同步此要求，不豁免正式 Review 或必需验证。

1. Reviewer 完成当前可进行的语义审查，记录被审修订、阶段、目标分支、范围、发现及处理依据；未完成的 CI 如实写为待完成，不提前写最终 APPROVE。
2. 在最终候选固定前提交正式 Review、所需规格和其他必要文档。文档可引用此前被审实现修订，不要求包含自身提交的 SHA；随后独立复核新增文档及受影响结论，将其纳入最终候选。批次 PR 创建后如需先取得编号才能落 Review，可取消被新候选取代的运行，但不得以其结果交付；不承诺绝无中间运行。
3. 对包含全部必要文件的最终候选执行阶段检查，批次出口执行 full；Reviewer 可并行检查剩余语义问题。若审查仍引出必须落盘的修改，形成新候选并重新验证。
4. 证据齐全后，Reviewer 在 GitHub PR/review 中确认最终 head/base、实际被测候选、正式 Review 文件及其适用性、检查 run/attempt 和批准范围。仅为回填成功日志、最终 SHA 或 CI 结论不再次修改仓库内 Review，避免自引用和额外候选；评论确认与 GitHub formal approval 的实际发布类型仍区分。
5. 实质性发现、处理结论或批准范围变化必须修订正式 Review 并重新审查、验证，不能只用评论掩盖已失实文档。最终确认晚于文件中的“CI 待完成”记录时，通过上述 PR 确认解释其历史时点，不把它改写为文档提交时已经通过。

子 PR 按当前阶段取得最终确认；批次最终 APPROVE 只在完整证据齐全后给出。main 合入后的独立检查结果及批次交付对账继续记录在 GitHub，不为补记运行结果制造新的主干提交。若某项既有特殊要求坚持将最终 CI 结果写回仓库文件，必须先明确处理该冲突；未解决前保留严格要求并接受新候选重验，不能同时声称消除了这类重复执行。

### 4.4 第二阶段：main 同代码树证据复用（尚未启用）

第一阶段完成真实平台试点、路由和保护验收后，才单独实施、审查及验收本节。第二阶段未启用或验收失败时，继续 §4.1 的 main full。阶段一不交付可提前启用的复用开关，也不将本节设为第一阶段完成前提。

第二阶段 main push 只允许从同仓库已合并的批次 PR 复用证据，并核对：

1. 该 PR 的实际合并提交就是本次 main push 的提交，不接受祖先 PR 或相似文件列表。
2. run/attempt 属于受信任的本仓库批次工作流及确切候选，full 和三个分片实际成功，不接受仅名为 `verify` 的任意检查。
3. 证据中的 base/head 与最终合入边界一致，实际 main 完整 tree 与被测候选 tree 相同。
4. 验证实现及锁定依赖属于该被测 tree；本次 PR 若改变验证机制则不使用批次复用例外。
5. 被复用门禁的相关运行输入相同或已经确定性证明不受差异影响，包括分支/ref、事件、环境与其他外部输入；不能仅凭 tree 相同或依赖有锁文件推定运行等价。不满足时执行 main full。

证据必须根据 Actions/GitHub 权威元数据核对；如使用运行产物，只解析声明数据，不执行其中内容，不把产物自报 PASS 当作成功证据。查无证据、API 不可用、候选不匹配或非批次 main push 均回退完整 full。main 运行保留独立 run，不相互取消。

第二阶段首版只支持普通 merge commit 的证据复用；其他方式不获得复用资格，执行 main full，且不能绕过合入前准入。复用结果明确写为“当前 main 代码树由指定候选 full 覆盖”，同时保留两者 SHA，不声称 full 曾在新的 merge SHA 上执行。复用仅适用于完成上述输入适用性核验的受控自动化门禁，不代替外部服务、生产部署或人工验收。

## 5. 主干保护与授权

2026-10-22 只读核对：main branch protection API 在沙箱和主机均返回 `Branch not protected`，仓库 rulesets 返回空集合。这是当时快照，实施前重读。

启用批次模式前应配置主干必须经 PR、必需 `verify` 与专用 `main-admission` 成功、要求当前基线验证，并限制直接推送和绕过；批次分支落实 §2 的阶段准入。业务交付必须在 main 之前完成 full，严格文档例外按 §2/§3 判断；不能只依赖 main push 事后发现。如果 GitHub 当前仓库能力不支持这些规则，报告阻塞并保留旧模式，不能宣称分支已受保护。

采用有限的工程引导顺序：先以明确列出范围的工程 PR，按旧 full 和独立审查交付新增检查，暂不启用批次轻量降级；确认检查能真实产生后，配置 main 与批次准入保护，再启用已审查的阶段路由并验证。工程引导例外仅用于这次切换，不能成为长期普通业务直达 main 的入口。切换验收失败时关闭批次降级、恢复旧 full 路由并保持已有主干保护；不得为解锁交付删除必需检查或宣称失败切换已生效。2026-10-23 的第一阶段启用及回退验收已获用户授权；其他范围的设置变更仍须对应授权。

分支保护设置属于外部仓库变更，需要明确授权。设计批准、子 PR 完成或 CI 成功均不自动授权创建/推送分支、发布 PR 或合并；用户可以单独授权指定批次的 Git 交付范围，授权在该范围内持续有效。

2026-10-23 用户明确采用单人开发并由本人批准。项目保留独立 Agent 审查、正式 Review 与人的合入授权；GitHub 不要求另一账户的 formal approval，main/batch 的 required approving review count 为 0，last-push approval 关闭。人的会话授权按确切任务范围记录到 PR，不伪装成 GitHub review。平台继续强制 PR、必需 CI、当前基线、对话解决及禁止强推/删除，无管理员或应用旁路；Agent 审查和人的授权由执行流程核对。此调整只改变批准的承载方式，不豁免阶段验证、累计审查或合入后的 main full，也不启用第二阶段。

## 6. 分阶段实施范围与验收

第一阶段实施涉及 §7 的共享角色支持，以及项目 `AGENTS.md`、验证基准 §2.1.1、必要的 target 说明、`.github/workflows/ci.yml`、准入检查、验证选择器/结果汇总及其测试，并按授权配置分支保护。第一阶段保留批次合入后的 main full，不实现或启用同 tree 复用工具。持久化分片和测试内容保持原覆盖，不把 Chromium 安装优化混入本次流程变化。

第一阶段验收必须覆盖：

- 同仓库批次子 PR 执行 docs/code；高风险工程门禁文件、外部 fork、未知 base/事件及无法读取 diff 不获批次降级。
- 批次 PR 即使只有文档或 UI 变化也执行完整累计 full；更新候选后旧 run 不能满足门禁。
- 普通业务 PR 即使在旧 UI allowlist 内、只有一个 PR 或标为紧急，也必须经批次；直接面向 main 被拒绝。严格文档和工程引导例外各有真实范围校验，未知资格不放行。
- 子 PR code 成功后将 base 从 batch 改成 main，即使 head 未变也必须重新路由并拒绝业务直达；旧 `verify` 或 skipped job 不能满足主干专用准入。批次 base 更新后，旧组合的阶段检查和批准也不能冒充新组合证据。
- 子 PR 完成不要求本地重复 full，且记录的批准范围不能误称主干交付或完整验收。
- 三个分片任一失败、取消、缺失或意外跳过均拒绝批次收口。
- 失败分类、冻结、聚焦修复、独立复核和新候选 full 可完整走通；代码改变不能拼接旧分片结果，外部失败不会被误写为代码缺陷或 PASS。
- 正式 Review 在最终候选固定前提交，最终确认可绑定该候选且不再产生仅回填日志的提交；实质性修订仍触发重新审查和验证，不删除正式 Review 要求。
- 第一阶段批次合入后 main 必定执行 full，不能因 tree 相同跳过；main 失败时暂停后续收口，单 PR 恢复批次仍经合入前 full/审查及合入后验证。
- 实际 GitHub 试点验证 main/批次保护、改 base、基线更新、合并生成的 tree、工程引导与失败切换回退；本地工具测试不能替代这些平台证据。

第二阶段在第一阶段验收后另行增加完整证据核验工具和对应 main 路由，保留前置准入。其验收必须覆盖：同仓库正确批次、精确 base/head/checkout/tree/workflow/run/attempt、全部任务成功和运行输入适用时可复用；错误或缺失证据、API 错误、不同运行输入及不支持的合并方式均执行 main full；实际平台验证复用与回退，明确未在新 merge SHA 上重跑的事实。第二阶段失败时保持第一阶段有效，不撤销批次路由、审查或主干保护。

工程规则与 CI 本身按原规则执行 full 并完成独立审查；本地验证不代替工程引导 PR 的最终候选远端 CI。通过后仍须获得相应授权，按 §5 顺序启用。首批选择一个明确目标和子 PR 集合试点，比较完整回归运行次数、批次反馈时间及修复轮次，运行记录放 GitHub PR，不创建平行状态账本。2026-10-23 试点修订时，远端启用和保护配置已执行，docs/code 子 PR、保护拒绝、旧基线阻挡、部分重跑拒绝及开关回退已有平台证据；业务直达 main 拒绝及恢复、最终批次 full、合入后 main full 仍待收口，详见批次 PR。此快照不替代最终候选验收；第二阶段证据复用未实施。

## 7. Vibe 角色与生命周期调整

共享技能支持项目显式选择批次交付，不把 `batch/`、PostgreSQL、三个分片或具体 target 写入通用角色。项目策略拥有阶段、分支和验证矩阵；未启用批次的项目继续既有路径。本节定义第一阶段已实施的共享规则；共享技能交付和项目远端批次启用分别验证，不能由前者推定后者已完成。

### Planner

Planner 同时明确一个完整交付目标和当前可独立实施、审查的子任务。一个用户结果不因前后端、数据库或文件数量自动拆成多个 Issue；只有依赖顺序、实现规模或可审查性确实需要时才拆分。子任务可以交付到集成分支，而用户可用与累计验收由批次承担。

利用现有 Issue 的 Scope/Verify 和关联链接说明所属批次、目标分支、当前阶段必须验证的内容及批次出口；不增加全局必填模板、状态文件或重复验收清单。批次目标与接受标准放现有交付计划或父 Issue，执行证据归 PR/CI。READY 表示当前子任务的依赖和验证可执行，不要求尚未实施的后续子任务已完成；需要前置子任务时依据集成分支真实状态判断。Planner 负责收口范围、移出子任务后的依赖复核及失败暴露的新设计决定。

同步校正 Issue Contract 的 Goal/Acceptance：批次子任务可声明有界、可验证的工程结果，父级保留完整用户可用目标；不能因旧模板的“完整可用”措辞重新要求每个子任务独立完成整个产品闭环。

按实际风险分类。已批准 T2 设计覆盖的子任务引用同一批准，不能每个子 PR 都重复请求相同设计批准；批准范围外的新决定仍重新规划。对已有 Issue 的 full 要求，先明确修订其阶段归属，再执行新矩阵；实现者无权自行降级。

### Implementer

在 preflight 中确认当前交付阶段、实际 base 分支、关联批次和本阶段 Verify，基于真实集成分支现状实施。不能只检查 main 后断言依赖缺失；也不能因同批另一个子任务尚未完成而自动扩大本任务范围。

继续先用聚焦测试定位问题，再完成本阶段配置检查。普通批次子任务不必完成后续批次 full 才可交给 Reviewer；有直接行为风险时执行相应的针对性检查，不因延期全量回归而省略本任务已约定的测试。需作为强制门禁的聚焦测试应有可执行、已配置的验证路径，不能把临时诊断伪称完整 Gate。

`PASS` 只表示当前阶段全部接受标准与必需验证满足，交接说明具体 revision、目标分支、证据和后续待验收边界。批次出口 full 不作为当前子任务失败，也不标为已经通过。已在当前阶段要求的失败测试仍必须修复；延期的是整批回归时点，不是已发现缺陷。批次收口时 Implementer 在既有授权范围内执行 §4.2 的集成修复，并在最终验证前纳入所需正式文档；不会因子 PR 已合入而把当前批次缺陷自动移为下一批。

### Reviewer

Reviewer 独立从项目策略、任务及实际 PR base/head 确定审查阶段，不能只接受 Implementer 的“子 PR”自报。子 PR 审查代码正确性、契约、安全、接受标准和阶段证据；本阶段检查全部满足时，可给出 `APPROVE` 并明确“仅可进入指定批次”。尚未到期的批次 full 不作为缺失当前证据的 REQUEST_CHANGES，已发生的相关失败不能忽略。

批次收口审查复用已有子 PR 的语义分析，集中核对最终累计 diff、跨子任务组合、冲突解决、未关闭发现、整批接受标准和最终候选 full。无需逐字重复此前所有审查，也不能把几个子 PR 的 APPROVE 相加当作最终批准。最终代码改变时复核改变及受影响结论，批准仍绑定最新候选。

保留既有结果 token，不新增 BATCH_PASS、INTEGRATION_APPROVE 或额外角色。正式 Review 记录语义审查阶段、目标分支及已知证据范围；最终 APPROVE 依 §4.3 在 GitHub 绑定固定候选、正式文档及完整证据，不自动授权 merge。整批 full 尚未完成时，Reviewer 可以先完成语义审查，但只能报告检查待完成，不能提前给出主干最终批准。修复后复核新增和受影响部分，不能将未解决发现随批次关闭。

### 共用规则与最小修改面

修改范围为 `SKILL.md` 的阶段性完成与证据解释、三个 role 文件、`issue-contract.md` 的 Goal/Acceptance/Scope/Verify 指引，以及 `execution-lifecycle.md` 的实现后交接、审查/CI 并行、失败修复和合入门禁；核对 `planning-lifecycle.md` 的交付对账措辞，明确集成事实与 main 交付事实。特别调整“所有本地验证先完成才能交接”为“本阶段必需本地验证完成”；后续交付阶段检查不前移，同阶段可信 CI 能否替代本地重复执行由项目策略明确。正式 Review 的具体收口规则仍由项目拥有。

执行仍沿用 Planner → Implementer → 独立 Reviewer；收口时由原执行上下文协调最终集成验证及 Reviewer，主干合入后由 Planner 对账。子 PR 合入只更新真实集成事实，不能把路线图的产品交付提前完成。不得新增自动 Agent 启动器、常驻协调角色或工作流状态账本。

同 tree 证据复用仅在项目第二阶段启用且通过确定性核验后成立，通用角色不凭模型判断把不同 SHA 当作同一验证。改 base、改阶段或改候选时重新判断证据适用性。未启用批次的其他项目继续原门禁；本项目启用后，普通业务直达 main、未知阶段或未配置的批次资格不能借“保留旧流程”获得准入。

角色规则验收包括：子 PR code 及约定检查通过且批次 full 未运行时可以阶段性交接；当前约定测试失败不能通过；已有 full 要求未修订不能降级；T2 子任务不重复索要已有批准；改 base 后旧阶段批准不可沿用；普通业务必须经批次；失败后原上下文继续有界修复并独立复核；正式 Review 与最终确认按 §4.3 收口；第一阶段 main full 未完成前不能宣告批次验证完成；其他未启用批次的项目保持旧流程。
