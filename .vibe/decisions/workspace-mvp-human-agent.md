## 1. 提案定位与权威边界

智举是 Human 与 Agent 共用的业务协作平台。Web 是人的工作台，公开 API/MCP 是 Agent 的业务入口，服务器 Agent 是受控执行者。MVP Web 不内置独立聊天 Agent；员工无需迁移日常对话习惯，也可直接通过 Web 完成适用的人工作业。

本文汇总已确认方向、提出兼容现有内核的设计增量，并显式保留未决问题。创建正式提案不等于全部技术选型、接口、运行时或上线条件已获批准；不将前期助手建议提升为用户决定。

## 3. Human、个人 Agent、服务器执行 Agent 的职责

```text
Human → Web / Feishu ───────────────────┐
                                       ↓
个人 Agent → 授权业务接入 → Public API → 智举 Core
                                       │
                            已确认范围与执行授权
                                       ↓
                             服务器 Runtime Adapter
                                       ↓
                    oh-my-pi / pi / qoder-cli / Claude Code
                                       │
                             候选输出、来源与执行收据
                                       ↓
                       Core 验证、版本、质量、人工确认
```

- Web 提供进度、成果检查、资料与意见提交、业务确认，不自行调用模型或拥有执行状态机。
- 个人 Agent 提交业务意图、输入资料和修改建议，读取被授权的项目上下文与结果；权限不继承员工全部 Human-only 能力。
- 服务器执行 Agent 处理授权范围内的文档；输出不因进程结束而自动成为已批准或已发布成果。
- Core 保有 Task/WorkOrder/Run/Result、Artifact/Revision、Quality/Approval/Release 的独立所有权及事实解释权。
- Agent 接入与运行时调用是两条不同边界。MCP 工具可用不等于可以远程接管个人桌面会话。

## 4. Web 产品结构建议

### 4.1 看板与工作详情

默认跨项目呈现需要介入的工作、进展和最近访问；支持按项目过滤。看板建议采用“需要你、推进中、待开始、已完成”四组，作为业务状态的展示分组，不新增同名 Core 状态机。

“需要你”保留缺少输入、成果待检查等具体原因。任务执行完成、交付项完成与项目交付进度分别展示，不从 Agent 自报完成推导项目完成百分比。Projection 延迟、UNKNOWN、拒绝与部分成功必须有可辨识状态。

2026-09-22 用户确认多份成果按就绪情况陆续交回：例如一项工作涉及 10 份文件，已有 3 份形成可审阅候选时，可先检查这 3 份，其余继续处理。看板同时显示待检查和仍在处理的文件数量，不等待全部完成才提供检查入口。数量来自服务端可核验的文件状态；运行日志或尚未形成正式候选的编辑中内容不计为待检查。单份候选可检查不代表该文件已满足批准条件，也不代表整项工作完成。

2026-10-07 用户确认新成果返回时保留当前页面，不自动打开文件检查页。看板原工作卡片更新待检查与仍在处理的文件数量，顾问主动点击“检查文件”进入；在其他页面工作时也不因候选交回强制跳转。后台刷新不得打断当前输入或阅读位置；正在检查的精确版本与未提交意见继续保留。该规则与“批准成功后自动进入下一份待检查文件”分别适用，后者仅由明确批准成功触发。

2026-10-07 用户选择本轮执行页以文件进度清单为主：直接显示每份文件的处理情况，已形成可检查候选的文件可进入检查；本轮范围、运行摘要和日志按需展开。清单支持文件名/编号搜索及状态筛选，长列表在视口内滚动，不把逐文件详情纵向堆满页面。仅纳入本轮已确认的文件；暂不能处理或未选择的文件继续留在分析总览，不混计入本轮执行进度。文件级状态与候选引用须来自服务端实际事实，不能用整体运行日志推测哪些文件可检查。

2026-10-07 用户确认处理失败的原因与重试入口在文件清单原位展示：原因在对应文件行下方醒目显示；服务端明确允许重试时，提供“重新处理本文件”，不先跳转失败详情页。操作只请求重试该文件，继续绑定本轮报告、完整计划和精确候选上下文，由服务端复核授权及执行条件；其他文件的候选、草稿与批准结果保留。已提交待核验、已接收待执行与实际处理中分别表达，不能把按钮点击或请求接收视为已开始；待核验时避免重复请求。失败运行历史与旧候选不改写，终态 Run 不原地恢复；真实重试/后续执行映射仍由 TaskExecution 契约决定，UI 不自行判断可重试性或切换运行时。

点击工作卡片进入固定高度的独立审阅工作区：左侧为当前工作文件列表，中间为文档阅读区，右侧为唯一的意见与处理区。页面不随文档长度持续增长；正文和长表在阅读区域内滚动。一次展示一处变化，通过上一处/下一处替换当前变化，同时保留所在章节或表格的上下文。

文件用途、编号、模板版次和候选轮次保留为标题下的一行辅助信息。变化详情默认打开，完整内容、资料与依据、摘要与关联在阅读区内按需切换，不在正文下纵向堆叠。右侧意见针对当前文件精确版本，可同时收集多处位置反馈；逐处浏览不是逐处独立批准，提交和批准粒度仍为单文件版本。

成果目录保持标准章节导航。MVP 中间阅读区展示 Markdown 的章节、表区及字段变化，并可核对完整文件；不以 Agent 摘要替代检查依据。宽表在阅读区内横向滚动，不省略列。Excel 预览、差异及转换后置。用户已确认此布局方向，间距、字号、提示文案等可根据上线后的使用反馈调整；版本、权限、反馈可靠提交及可访问性基本要求仍需在上线前验证。


### 4.2 一个反馈入口，不增加聊天助手

当前工作中的问题回答、修改要求、附件与定位引用集中在一个反馈区域。它提交明确关联的业务内容，不运行一套独立 Web Agent。复杂意图由受控服务器流程处理；无法确定范围时产生具体澄清项，不伪装已执行。

区分未提交草稿与明确提交的修改请求。用户于 2026-09-22 确认：当前文件的主要动作命名为“提交并修改”；该动作同时表达提交意见和请求服务器开始处理的意图，不再要求另点“开始修改”。人工批准和发布仍单独呈现精确对象与条件；输入框中的草稿不构成执行授权。新反馈如何转换为后续 WorkOrder，须完成 §8 的业务契约设计。

Web 发起新工作时先明确项目，再描述目标、附上资料，入口规则见 §4.7。用户确认新工作先由服务器整理范围，集中展示目标、使用资料及预计涉及的文件，确认后才开始生成或修改文件；请求整理与正式执行的 owning 契约仍需细化。Web 无 Agent 不等于禁止后台 Agent 协助整理请求；也不意味着引入自主复杂 Coordinator。

用户于 2026-10-07 确认旧基准 Markdown 改稿的复核交互：附件沿用当前文件的唯一意见区，原基准由顾问明确指定并绑定精确版本，不能从文件名猜测或随着新候选自动改绑。提交保留改稿、旧基准、提交时的新版本及附加说明各自快照；运行中的新意见与新附件作为未提交草稿保留，不自动加入已发请求。复核返回新候选时继续保留当前页面和正在查看的版本；遇到待判断事项时在原意见区反馈并保留原请求，意见或复核回执本身不解除冲突。该选择是产品交互决定，尚不注册新公共 Schema，也不改变 owning Module 的版本、质量与授权规则。

### 4.3 多入口接续

入口共享正式任务、成果和反馈，不强求复制全部聊天记录。业务上下文包括目标、确认要求、精确输入版本、成果引用、未解决问题及人的反馈。

Web 提交意见后无需再次复制回个人 Agent。点击“提交并修改”后，范围明确且只涉及当前文件的请求，在服务器校验当前授权、精确版本和执行条件后进入处理，无需第二次启动操作；涉及其他文件或要求不明确时，先取得范围确认或澄清。状态区分未提交草稿、已提交待执行、执行中及结果待检查；已接收或排队不显示为已经开始修改。主动通知、轮询和下次查询分别适配，不承诺所有工具都有推送能力。

手机在“查看文档”和“意见与处理”之间切换，引用变化后进入同一个意见视图；不同时挤入桌面三栏。手机主要支持查看与轻量处理，复杂检查及批准范围沿用正式 UI Gate 决策。历史常驻聊天助手原型属于探索，不是本提案的正式实现依据。

### 4.4 已确认的逐文件检查交互

以下规则来自本提案建立后的用户逐项确认，属于产品交互决定，不代表相关 Command、状态映射或授权增量已经实现。

| 场景 | 已确认行为 |
|---|---|
| 从看板进入工作 | 进入独立工作详情页，处理后返回；不以侧边抽屉作为主要工作空间 |
| 本轮多份成果 | 左侧紧凑成果列表，中间阅读区，右侧唯一意见与处理区；列表限定当前工作成果 |
| 多份成果交回节奏 | 2026-09-22 用户确认：形成可审阅候选的文件陆续交回，顾问先检查已就绪文件，其余继续处理；看板同时显示待检查与仍在处理数量。每份文件批准仍须满足实际质量、版本及授权条件 |
| 需要修改 | 单份文件检查后点击“提交并修改”，一次操作提交意见并请求服务器开始处理，不等待整批或第二次启动；提交成功后留在当前文件，MVP 不自动切换。范围扩大或要求不明时先确认/澄清 |
| 修改进行中继续补充 | 2026-09-22 用户确认：同一个意见框允许填写下轮草稿；不打断本轮执行、不自动发送或并入本轮要求。新版本返回后，用户核对内容与引用位置，再点击“提交并修改” |
| 无需修改 | 在当前页逐份检查并批准具体版本，不等待整批集中批准；必须满足真实质量与授权条件 |
| 提交回执不确定 | 2026-10-08 用户选择短时自动核验，并在体验原型后确认保留核验提示在原意见区顶部（桌面为右侧，窄视口为“意见与处理”视图）：单份修改请求提交后若未收到回执，原意见区显示“提交结果待核验”；保留提交时的精确项目、文件、基准版本、意见及附件，查询同一次请求。短时仍未取得确认时停止自动核验，提供“重新查询”；查询不会重发意见或启动第二次修改。可继续写下轮草稿，新输入不并入原请求。只有匹配原请求与上下文的权威回执才能确认“已接收，等待安排”或“正在修改”；查不到、超时或上下文不匹配均不推断为失败、未接收或成功。不跳转、不替换阅读版本，不按成功批准或推进下一文件。自动核验预算、公开查询接口、安全折叠、授权和跨设备恢复待 UI-DG-003 与 owning module 对接；合成原型不代表上述集成已验收 |
| 批准成功 | 自动进入下一份待检查文件；批准失败或结果 UNKNOWN 时不按成功切换 |
| 新版本交回 | 用户主动切换到新版本后默认显示变化详情；上次意见与处理摘要在“摘要与关联”视图按需查看，保留本轮其他改动及完整文件入口；Agent 自报已处理不等于检查通过 |
| 检查中发现新版本 | 保持正在查看的旧版本及未提交意见，提示新版本，由用户主动决定切换；不自动替换正文 |
| 默认阅读顺序 | 首次进入、切换文件、批准后进入下一份及查看其他版本均以变化详情为主，一次一处变化；摘要通过辅助视图查看 |
| 辅助信息 | 文件身份为一行；一般提示和关联文件在辅助视图查看，不纵向追加到正文；真实阻断问题保留紧凑醒目的提示 |
| 阅读空间 | 页面高度受视口约束；长文与表格在阅读区滚动，逐处导航替换当前变化，意见区独立保留 |
| 窄视口 | 文档和意见分视图切换；引用后可直接写意见；支持矩阵已按 UI-DG-002 冻结，具体响应式细节按已批准视口验收 |
| 位置反馈 | 从章节、表格、适用性问题或关联关系引用到同一个反馈入口；不增加各处独立输入区 |

### 4.5 关联影响的分工与范围确认

单文件修改涉及其他成果时，先提出关联修改建议，由 Human 确认是否扩大范围。已确认由服务器 CC/OMP 分析语义影响，业务服务校验和保存建议、组织确认，Web 展示并收集决定。

### 4.6 适用性展示与原型边界

用户接受了工作页中的适用性提示、引用查看、内容定位与单一反馈入口；这属于展示和操作方向确认。实际哪些问题阻断批准、谁能确认、确认绑定哪些版本与证据、变更后是否需要重评，仍由 owning 业务规则决定，并须完成 D10/Q10 的契约设计。

采购申请单原型使用“客户是否存在研发样品采购”的合成待确认场景。底部“演示：当前范围已确认”只是模拟已取得确认结果，不是拟上线的业务按钮。提交自由文本不会自动解除阻断；当前演示只对本轮候选记录确认，新版本不会继承。不得据此推导生产规则一律按文件轮次重新确认，或浏览器可自行解除 Quality Gate。

章节/表格引用在原型中以模板文本位置展示；正式反馈须使用精确 RevisionRef 与受支持的稳定内容定位。源文本行号不等于 Canonical Unit ID。读取关联文件不表示必须改写，文件被多处引用也不应复制成多个互不关联的正式身份。

##### 顾问的操作顺序

1. 在现有新建入口选择/新建客户并填写项目名，服务器建立准备项目；成功后直接到本项目 ZIP 页。创建本身不启动分析或生成。
2. 一次提交一个 ZIP 和可选说明。服务器接纳原包，受控解包并保存逐件来源、Hash、实际支持/不支持及准备结果；分析请求锁定本次资料清单与公司模板/规则版本。顾问上传不要求预先确认整套 CustomerBaseline。
3. 服务器 Runner 先读客户文件，再比公司模板，返回分析报告和必要启动信息建议；顾问进入已确认的四区总览。平台不新增正文分析 Agent。
4. 进入现有“选择本轮文件”面板时，集中展示尚需核对的必要启动信息及其客户依据，并展示默认不选的文件范围；无需另开企业画像维护流程。提交文案须明确同时确认信息与本轮范围，不能把普通“查看报告”或“提交补充”当成启动批准。一个界面操作可以协调多个 owning Command，但各个 Human 决定、启动和工作范围仍有独立精确引用与回执，不宣称跨 Aggregate 原子成功。
5. 必要信息由有权限的 Human 核对后，EP 创建真实 Fact/Product/QMS/Profile/产品范围引用并一次性冻结启动绑定。只有正式启动成功且本轮范围、保护和依赖条件均满足，才能创建后续文件升级工作。待补文件和不影响独立文件的未知信息可以继续等待；会影响必要启动引用的缺口则必须先补齐，不能靠“部分可做”绕过启动条件。

已有客户可以引用仍然有效且与本项目范围匹配的精确企业版本；界面先显示所用版本及来源，再由有权限的 Human 确认，不能自动取 latest。新项目的资料、报告和文件处理仍按 Project 隔离；报告不会无声改写其他项目的启动绑定或企业事实。

##### 一致性、兼容与失败恢复

- 现行完整创建路径仍在单个事务创建 ACTIVE Project 和启动绑定；历史 ACTIVE 项目不回退到 PREPARING，历史 Snapshot/Receipt/Context/Contract/Result 不改写。forward migration 必须从可验证历史绑定确定旧创建模式，不凭“查不到绑定”将损坏旧项目标成准备项目。数据库应区分合法新准备创建与旧完整创建，防止直 SQL 生成缺启动绑定的 ACTIVE 行；同项目的 Scope、memberPolicy 和唯一启动绑定仍不可变。
- 新建客户和创建准备项目是不同 Aggregate，不能承诺全有或全无。若客户创建成功而项目失败，保留客户及第一步回执，按同一意图稳定键回读并继续项目步骤，不重复建客户、不自动删除客户。已有客户选择按精确 ID 与当次可见权限核验，不按名称去重或合并。
- 上传、解包、调度各有可回读状态，网络和进程不进入 owning 数据库事务。解包失败不调 Runner；客户原件保留，不支持、损坏或读取受限的文件明确列出；没有真实报告不能展示“已完成分析”。输入目录中的同名文件保留各自来源身份，不以文件名/内容 Hash 单独消除来源。
- 请求超时保持 UNKNOWN，使用原意图、原稳定键和原 payload 回读；不因刷新或二次点击产生新项目、新分析调用。Runner 失败后只能按服务器允许的显式重试创建新的执行尝试，旧 Attempt/Report 不被覆盖。输入或模板变化形成新分析请求和新清单快照，原 Run 不偷换输入。
- 报告错 Scope、Hash、来源清单、原 Invocation、路径或 JSON/Markdown 绑定时隔离；仅合法报告可进入业务快照。技术校验通过和 Runner 自报 READ/检查通过不等于业务语义正确，读取覆盖与限制仍交给顾问核对；迟到报告保留历史，不覆盖较新报告/待提交草稿。
- 启动时重验当次权限、当前准备项目版本、所确认报告/输入及候选精确引用；并发报告或材料变更导致所确认输入过时时，保留草稿并要求重看受影响部分。已启动后的新资料走新报告/影响评估，不替换冻结启动绑定。某一步确认成功后下一步失败，保留已提交事实和回执，按实际阶段恢复，不把整组操作标为全部成功。

补充草稿、已提交待核验、核验后等待执行及实际执行须清楚区分。上传或提交成功不等于资料已采纳、阻塞已解除或后续处理已开始；局部补充不清除其他缺口。已提交内容及回执保持可追溯，未提交的后续草稿不自动发送。该场景针对系统明确提出的补充问题，不将执行期间自由填写的下轮草稿自动纳入当前要求。

本决定合并前台提交与请求继续的动作，不合并 Answer、CustomerMaterial 确认、Request Resolution 与执行授权等业务事实，也不扩大 Human 权限。接续由 owning 服务按正式结果组织；final BLOCKED_INPUT 后须按契约创建新 ContextSnapshot 和后继 Run，不原地恢复终态执行记录。字段映射、补充事项 Profile 和公开接入仍须在 D05/UI-DG-003 中细化；当前只批准产品交互。


### 4.10 正式交付包与人工发送

2026-09-22 用户确认 MVP 正式对外交付采用“生成交付包，由顾问发送”：顾问明确确认本次交付的文件与精确版本，在满足适用发布条件后取得下载包，沿用已有飞书、邮件等渠道自行发送。MVP 不建设系统直接向客户发送的入口；这不限制日常查看或授权下载候选文件，也不将候选下载视为正式交付。

界面只按真实结果呈现包的准备、生成及可核实的下载情况；生成包或点击下载不自动表示正式对外发送成功、客户已收到、客户验收完成或项目已完成。交付内容保留文件身份和精确版本；准备后出现新候选，不得静默替换已经确认或冻结的内容。用户进一步确认允许按阶段分批交付：顾问选择本次交付范围，例如先交付采购部分，每批固定文件清单与精确版本；其他成果继续推进，不要求整项目的全部成果先完成。每批仍须满足相关配套文件的完整性与适用发布条件，不因允许分批而跳过依赖。用户于 2026-10-07 确认交付准备按项目汇总：不同执行轮次中满足条件的获批文件统一沿体系章节组织，顾问逐份选择本批文件并集中确认精确版本。执行轮次与所依据报告保留为逐文件来源信息，不作为拆分交付包的依据。此前获批范围、候选、个人草稿及已有交付包均保持各自状态；内部批准本身不证明发布资格或配套完整性。交付包汇总的具体对象和接口仍待设计。

用户进一步选择 B：MVP 只记录交付包与下载情况，实际发送继续在外部渠道管理，不增加“标记已发送”、发送人/发送时间登记、客户收件或验收状态。界面必须区分可核实的服务端下载响应与浏览器下载请求；只能证明发起请求时，显示“已请求下载”，不能显示已保存完成。该选择收敛前端范围，不删除既有正式发布回执能力。

当前契约存在需要明确处理的边界：本轮核对本地主工作区的 [ReleasePublication Spec](../module-specs/Module-Spec-006-ReleasePublication.md) §2、§7、§11.2，现有 Release/ReleasePackage 绑定一个 Artifact/精确 canonicalRevisionRef，可包含该版本的多种 Representation 及多个 Destination；其 representations 不是任意多份文件的版本清单。Issue #260 的 [D12/Q11 Spec Delta](project-delivery-controlled-export.md) 提出 ReleasePublication-owned Batch 引用逐文件已授权 CONTROLLED_EXPORT Release/Package、独立Manifest/ZIP Hash及请求/响应观察；仍为 PROPOSED / FUTURE DESIGN / NOT REGISTERED / NOT IMPLEMENTED，待独立设计审查及精确修订人类技术批准。不能直接改写既有 Package Hash 域、将多个版本装入单 Revision 契约，或用浏览器压缩下载绕过正式发布条件。

现有 Package 还要求精确接收方/目标及正式发布回执来源；人工离线发送不能被伪造为 PublicationReceipt。正式实现前，需明确受控导出路径、面向客户的多文件下载集合与逐文件 Release 的映射，以及此阶段能够证明的事实。该产品选择不冻结新 Aggregate/API，也不删除既有对外发布能力； owning Spec/Test/Contract 的增量按后续设计审查同步。

## 5. 客户输入、Markdown 工作格式与内容版本

客户输入现接受 DOCX / Markdown，平台解包并由 Runner 阅读、分析和生成；成果仍为 Markdown。该决定不增加 Web 内 Word 编辑或 DOCX 输出，也不改变 Canonical Source of Truth。

需要冻结：

1. Markdown 支持语法、图片/附件及证据引用、稳定段落身份映射和不支持内容的处理。

3. 原始文件、规范化内容、执行输出、候选版本与下载表示之间的来源及 Hash 关系。
4. 导入与再生成的差异检测；不支持内容必须报告，不能静默丢失。
5. 空白模板与真实业务记录分别处理；修改表格结构不能默许改写历史数据。

MVP 最终交付格式已由用户确认：

2026-09-22 用户确认本地改稿的 MVP 默认策略：接收 Markdown 作为修改建议，绑定当前 Artifact 及修改所基于的精确 Revision，由服务器比较并按受控流程产生新候选；上传不直接覆盖成果，也不成为已批准版本。个人 Agent 的文件内容是输入建议，其指令或配置不替代公司执行方案。用户进一步确认 MVP 每次只接收一份改稿，绑定当前正在检查的文件；首版不提供批量改稿及逐份匹配页面。该限制不决定首次客户原始资料的导入粒度，也不授权任意格式导入或直接 Human Edit 写入正式版本。

交互建议：在当前文件的同一意见区附上改稿，显示文件名与基准版本，沿用“提交并修改”动作；选取或上传附件本身不启动修改。附件保存与个人草稿的关系、版本已更新时的处理，以及建议到新候选的字段级契约仍需收敛。原始客户资料的接纳与本地改稿保持不同语义，不能仅凭扩展名判断用途。

### 5.3 Markdown 填写与后置的 Excel 转换

MVP 的主链路是 Runner 先读客户体系文件，再比对公司 Markdown 模板，在保护企业方针、目标、人员组织、既有流程和产品规定的前提下提出升级计划，确认后形成 Markdown 文件级候选。需要新增表单时基于模板及经确认的企业事实处理；空白模板、客户适配表单、已填写业务记录继续区分。一份文件独立编号、版本管理、检查及批准，生成或填写完成不表示客户已签批或系统已发布。

### 7.2 BFF 与部署方案（工程选择已批准，尚未验证）

推荐独立 `apps/workspace-bff` 进程，沿用现有 Node/TypeScript 与 NestJS/Fastify 技术方向以减少服务端技术分叉。首次部署可与 Core 同机，仍保持进程、配置与发布边界；无需为 MVP 引入微服务集群或微前端。仓库内独立应用不等于独立仓库，也不要求独立域名。

```text
Browser → 同源反向代理
            ├─ 静态资源 → workspace-web 构建产物
            └─ Web 会话/页面读取 → workspace-bff
                                      ├─ Keycloak：OIDC
                                      └─ 公开 HTTP API → owning Core Service
个人 Agent / 服务器 Runtime → 各自授权业务与执行入口（不经过页面）
```

路径前缀属于后续 Experience 路由设计，不在这里发明公开业务 Command。BFF 可以组合已授权 Query，不能用一个页面动作同步写多个 owning module。命令仍通过现有公开契约指向唯一 Owner；只有公开 API 准备好，相关页面才可接入。

继承既有 OIDC Code + PKCE、HttpOnly/Secure Cookie、CSRF、Origin/Host 校验及 token 服务端保管规则。建议部署为同源 Browser/BFF；认证由 Keycloak 证明，业务权限由 IdentityPolicy 决定，不能以 UI 隐藏按钮替代服务器拒绝。

UI-DG-003 的技术 Session、Cookie/OIDC、超时/刷新、CSRF/CSP/Markdown、代理/下载与脱敏方案已在工程基线获批，仍需独立审查及真实实现验证。个人草稿的 owning 持久化接口仍为后续业务依赖；技术 Session 不保存业务草稿，本节不宣称认证已上线可用。

## 10. 正式业务验收场景（前瞻要求，均为 NOT RUN）

1. Human 无需使用 Web 聊天助手，可通过 Web 提交明确范围的工作并查看执行结果。在项目内发起自动带入当前项目；从跨项目首页发起先选择项目，再描述目标和附上资料；项目归属与权限由服务端核验，不从自由文本静默推断。服务器整理目标、使用资料和预计文件范围并展示一张确认卡，用户点击“确认并开始”后才启动文件生成或修改。
2. 个人 Agent 在授权项目提交请求；不能访问其他客户、直接 READY、覆盖受控版本或执行 Human-only 批准。
3. 同一任务可从外部入口进入 Web 查看精确成果；Web 反馈无需手动复制回外部工具。
4. 服务器执行使用锁定方案版本；上传的指令文件和个人配置不能改变工具授权。
5. 重复提交、并发执行、旧版本意见、超时 UNKNOWN 和 late result 不产生重复有效执行或覆盖。
6. 正常闭环与补充输入闭环有正式业务证据；已确认范围内且有权确认的补充事项通过“提交并继续”一次提交并请求接续，不要求额外启动。核验未通过或仅补齐部分事项时保留其余缺口；等待核验、等待执行及执行中可区分，不能仅凭提交成功解除阻塞。扩大范围仍须确认；terminal Run 不以聊天“继续”原地恢复。
7. MVP 接受 DOCX/Markdown 客户资料及 ZIP 批量容器，后台受控解包后由 Runner 读取分析；受支持内容形成 Markdown 候选并可检查输出。读取限制、不支持内容显式报告；原件、企业保护内容、历史记录、表格字段及引用无静默改写或丢失。
8. 看板区分工作执行、成果检查、批准与交付；陈旧 Projection 不显示为当前权威状态。多份成果陆续交回：10 份文件中已有 3 份形成可审阅候选、7 份仍在处理时，可以进入检查这 3 份，并同时看见两类数量；批准仍逐文件满足实际条件，不能据此显示整项工作完成。新候选交回时保留当前页面、阅读位置、正在检查的版本和草稿，不强制打开检查页；只有明确批准成功后才自动进入下一份待检查文件。本轮执行页以可搜索、可筛选的文件进度清单为主，已就绪项直接进入对应文件检查；运行摘要与日志按需展开，未纳入范围的文件不计入本轮。
9. 运行时失败、客户端离线、通知不可达时，任务仍可查询且状态真实。文件处理失败的原因和服务端允许的单文件重试入口原位显示；重试不覆盖其他文件的结果、不改变旧候选和失败运行记录，也不把接收回执显示为已经执行。服务端未允许或尚未核验时不能发起直接重试；正式重试及后续 Run 证据仍为 NOT RUN。
