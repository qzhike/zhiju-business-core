# MVP 上传拒绝嵌套压缩文件

日期：2026-11-03

状态：`PRODUCT AND TECHNICAL DESIGN APPROVED 2026-11-03 / IMPLEMENTED LOCALLY`

## 1. 已确认的目标与范围

用户要求移除嵌套 RAR 处理，并在上传时检查嵌套压缩文件，发现后要求用户移除。此决定取代此前 MVP 必须读取 bopu 嵌套 RAR 成员的要求。平台不解包、转换或静默跳过内层压缩文件；用户可以自行解压所需资料，放入普通目录后重新制作一个 ZIP。

完整用户结果：用户上传一个 ZIP 后，系统明确告知是否接纳；若包含嵌套压缩文件，则整批拒绝，列出包内路径和整理方法，用户换用整理后的 ZIP 可以重新上传。首次和补充批次遵守相同规则。

本工作为 T2：用户已经决定接纳策略，但实施需要输入 policy 升版、数据库兼容迁移及批次详情的附加拒绝信息。用户已于 2026-11-03 批准以下技术增量；批准范围为本地实现和验证，不包含现有实例迁移或部署。影响范围仅为 DocumentDelivery、其 MVP API/BFF/Web 入口、M1 演示数据及拥有这些行为的 Spec/Test。外部 Runner、旧七模块接入链、客户原包和模板不修改。

## 2. 实现取舍

- 后端在外层 ZIP 的安全解析后、任何成员接纳或 manifest 封存前检查全部普通文件。任意嵌套压缩文件使整批进入既有 `REJECTED`，不形成部分成功的 manifest 或 ACCEPTED_ENTRY。原始上传对象沿用现有隔离保留规则，不对外提供被拒批次的内容下载。
- 检查包内任意目录深度的普通文件，结合扩展名与常见文件签名，不打开或递归解压内层压缩文件。覆盖 ZIP/ZIPX、RAR 及常见分卷、7z、TAR、GZ/TGZ、BZ2/TBZ/TBZ2、XZ/TXZ、ZST/TZST、LZ/LZMA/LZ4、Z、CAB、ARJ、ACE、LZH/LHA。ZIP、RAR、7z、gzip、bzip2、xz、zstd、TAR、CAB 的已知签名不能通过改名为普通文本绕过检查；未知格式仍按已有不支持规则处理，不声称能识别任意私有格式。
- DOCX/XLSX 的正常 OOXML 封装是文档格式，不是用户需移除的压缩文件。对带 ZIP 签名的 `.docx/.xlsx`，先识别是否具有 OOXML 包级结构依据，不能只凭扩展名豁免。没有 OOXML 结构依据的普通 ZIP 即使改名为 DOCX/XLSX，也按 `NESTED_ARCHIVE_NOT_ALLOWED` 整包拒绝，不能仅标记为损坏文档后部分接纳。具有 OOXML 容器结构依据但内部文档损坏、包含活动内容或外链的条目，仍沿用既有 CORRUPT / UNSUPPORTED / READ_LIMITED 规则；结构身份识别不等于完整文档校验通过，累计预算检查不变。普通文件夹、文件名中间的 `.rar` 字样不应误判；真正压缩扩展名按大小写不敏感判断。
- 前端显示“资料包包含嵌套压缩文件，已拒绝接纳。请解压需要保留的资料，将文档放入普通文件夹，移除内层压缩文件后重新打包上传。”拒绝详情列出全部命中的包内路径，按不可信文本渲染。用户整理后创建新批次，不能用原请求或原批次覆盖不同字节。
- M1 合成数据移除 RAR 容器、模拟内层成员及“继续分析未读 RAR”的路径；普通目录、损坏文档、读取限制及来源历史继续保留。移除 RAR 专属成员分组和计数分支，不删除客户数据，也不把历史 Runner 报告中的真实限制改成已解决。

## 3. 已批准 Spec Delta

字段和失败语义进入 [MVP01 Spec 的已批准增量](../module-specs/Module-Spec-MVP01-DocumentDelivery.md#8-上传拒绝嵌套压缩文件)。本设计仅拥有以下取舍：

1. **policy 升版。** 新批次固定 `mvp.zip-input@2`，新提取器标记 `mvp.input-extractor@2`。现有数据库将 policy 限死为 `@1`，通过新增迁移允许两个版本；不修改旧迁移文件、不回写旧 receipt/manifest。
2. **拒绝原因与路径。** 增加 `NESTED_ARCHIVE_NOT_ALLOWED`。批次详情可返回 `rejectedArchivePaths`，仅用于该原因的已拒绝批次；路径来自完整安全扫描，最多受已有 1000 entry / 每路径 240 UTF-8 bytes 预算限制。路径不进入通用日志、技术头或原因代码。批次表新增拒绝路径 JSON 字段，在拒绝状态提交事务中保存，沿用 owner/project 隔离；刷新及重启能读回同一结果，无需重复扫描整个 ZIP。
3. **旧批次边界。** 已封存或终态的 `@1` 批次保持只读历史，升级不重新解释旧结果。新版本不自动续跑旧 policy 的未完成上传/提取；已证实结束的旧尝试通过显式放弃后新建 `@2` 批次。尚未确认结束的写者先走原尝试核对，不能凭 policy 变化强行清除活动占用。不得后台批量删除、重置或重传旧批次。
4. **事务和恢复复用。** 不新增业务状态或通用执行框架。仍使用既有 Request、Attempt、REJECTED、当前授权检查和进程锁；拒绝与释放本批活动占用同事务完成。同键重放返回原结果，拒绝后允许用户新建修正批次。

不得扩大旧批次恢复动作绕过实际写者结束证明。新字段和迁移映射同步到共享 MVP API、07 持久化增量及 owning Spec/Test；本地实现不等于现有实例已迁移或发布。

## 4. 验收与交付

最小完整实现包括后端阻断、持久拒绝详情、上传页提示和改正后再上传，以及 M1 演示/当前产品要求的同步，不拆成前端看似可用但后端仍部分接纳的结果。

验收场景见 [MVP01 Test](../module-tests/Module-Test-MVP01-DocumentDelivery.md) 的 NA-01–06 和 [UI01 Test](../module-tests/Module-Test-UI01-WorkspaceUI.md) 的 UI-MVP-M1-048。重点是：嵌套压缩文件整包拒绝且零业务 source/manifest；大小写、改名签名和目录层级；正常 DOCX/XLSX 不误拒；修正后新批次成功；拒绝路径在刷新/重启后仍可读；旧批次/旧请求与当前授权不被改写。

先运行聚焦 scanner、HTTP/持久化及浏览器用例，最终使用 `vibe verify full --json`，新或变化的容器环境先运行 `vibe verify environment --json`。此前用户免除数据库测试的范围为纯 UI 调整，本工作包含后端接纳和持久化，不能以 `code` 代替。最终实现需独立审查；尚未执行的真实环境、用户整理后输入及人工验收保持 `NOT RUN`。

当前原始 bopu 包含两个 RAR，保留为拒绝反例，不改写原包。成功上传和业务内容验收改用用户重新整理并确认的无嵌套压缩文件 ZIP，重新固定其摘要和实际文档清单；不把旧容器统计自动当作新输入数量。
