## 1. 目标、依据与授权边界

用户已批准“业务文件与 Office 内部部件分开限制，并明确显示超限种类、实际值与上限”的修正方向。本提案给出该方向所需的具体额度、版本及持久化增量。分类为 T2：修改已冻结的 ZIP 安全接纳预算，并增加持久拒绝详情；用户于 2026-11-04 回复“批准”，批准绑定独立审查通过的设计 SHA-256 `25382b18c10119a595ea76cf6d9f764f4f57bf589f86241d23cabf204f66b63f`。本地实现与验证、指定 Tailscale 测试实例升级已获授权；不因此取得 Git 提交、推送、合并或真实资料自动重传授权。

修正前 `@2` 的 [MVP01 Spec §5](../module-specs/Module-Spec-MVP01-DocumentDelivery.md#5-zipdocx-与-xlsx-接收-policy) 将外层 ZIP 与全部 DOCX/XLSX 内部条目共享 1000 条预算。只读测量两个已上传原包：外层分别为 99/198 条，其中普通文件 93/192 个；均包含 55 个可识别 Office ZIP、1334 个内部部件，单份最多 42 个部件，外层加 Office 累计展开约 17.6/14.7 MiB，最高内部压缩比约 24.98。现有扫描分别在累计 1007/1026 条时拒绝。这证明当前配额口径阻断了本批正常规模的资料，不能据此声称所有文件内容、安全或后续业务验收通过。

客户原包只读用于本机诊断，不提交到仓库、不改写或自动重传。样本中以 Office 扩展名结尾但不具 ZIP 结构的附属文件仍按现有格式规则处理；本提案不增加系统杂项自动过滤，不放宽嵌套压缩文件、CRC、路径或活动内容检查。

## 2. 已批准的新预算与版本

新批次固定 `mvp.zip-input@3`，新成功 manifest 固定同一 policy 与 `mvp.input-extractor@3`。只修改新 MVP 的 DocumentDelivery，不改变旧 IntegrationGateway/D14 的 policy。

| 计量 | 新上限 | 计数口径 |
| --- | ---: | --- |
| 外层 ZIP 条目 | 1000 | 包含外层文件与目录，沿用原外层上限；UI 明确写“文件与目录条目”，不称为纯文档数量 |
| 单份 Office 内部条目 | 1000 | 该 DOCX/XLSX 的全部内部条目，包括目录；保留旧规则隐含的单容器上限 |
| 全包 Office 内部条目 | 20000 | 所有 DOCX/XLSX 共享；不随文件或格式校验失败重置 |

20000 是本提案的有限工程额度，为目前实测 1334 个部件提供余量；不表示任意 1000 份 Office 都保证可接纳，也不是经过负载验收的容量承诺。单份上限防止一个文档独占总预算。目录、损坏 Office、伪装 Office 中已检查的结构仍消耗预算；不能通过重复失败、改变扩展名或重建局部计数器绕过限制。

原 ZIP 100 MiB、外层与 Office 累计展开 500 MiB、单条目 50 MiB、展开倍率 100、路径 UTF-8 240 bytes / 16 层、120 秒、512 MiB 工作内存保持原值。字节、内存、耗时预算仍由整次扫描共享，CRC/实际长度仍须验证，不只信任 ZIP 头部。普通嵌套压缩文件继续整包拒绝且不递归展开；Office 身份仍须 OOXML 结构证明。

## 3. 可解释的拒绝事实

保留兼容原因码 `ZIP_LIMIT_EXCEEDED`。`mvp.get_input_batch` 的 data 新增可选闭对象 `limitViolation`；新 `@3` 批次因该原因进入 REJECTED 时必须保存该对象，其他原因省略。旧 `@1/@2` 记录缺少细节时保留原结果，不能根据新限制倒推数值或改写历史。

详情采用有界 tagged union，精确字段在批准后同步到 owning Spec 与读取模型：

- 常规计量：`{ metric, actual, limit, documentPath? }`。`metric` 闭集为 `ZIP_BYTES`、`OUTER_ENTRIES`、`OFFICE_DOCUMENT_ENTRIES`、`OFFICE_ENTRIES`、`ENTRY_BYTES`、`EXPANDED_BYTES`、`MEMORY_BYTES`、`PROCESSING_TIME_MS`；actual/limit 为非负安全整数且 `actual > limit`。actual 表示下表规定的计量值，不统一解释为已经读取的实际数量；limit 必须与该批 policy 的计量值一致。
- 展开倍率：`{ metric: 'EXPANSION_RATIO', expandedBytes, compressedBytes, limit, documentPath? }`。两字节值为目录声明的非负安全整数，limit 为 100；仅在声明压缩字节为 0 而声明展开非零，或声明倍率大于 limit 时合法。使用字节对保留精确依据，不用 Infinity、NaN 或编造的整数倍率；UI 显示“目录声明的展开倍率”，或“目录声明压缩大小为 0、展开为 N 字节”，不声称已经实际解压出这些字节。
- 可选 documentPath 仅允许来自已经完成外层安全/完整性解析的原始 Office 文件路径，最多 240 UTF-8 bytes，并保留原文本。外层计数、路径、CRC 尚未验证的错误不得附加从不可信目录猜出的路径；内层部件名称、宿主路径、栈和原文不对外返回。
- 只保存扫描遇到的第一个超限事实，不声称已经统计完整包。限额被触发后立即停止本轮解析，不为展示继续解包；伪造的目录声明仍可先触发安全预算拒绝，不能据此对外声称实际读取了该数量。

计量依据由 metric 固定映射，作为该版本协议的一部分，UI 不推断来源，也不增加任意 basis 文本字段：

| metric | 固定依据与页面表述 |
| --- | --- |
| ZIP_BYTES | 当前输入 Buffer 的真实长度；“压缩文件大小” |
| OUTER_ENTRIES | 外层 ZIP 结束目录声明的条目数，可能早于目录逐项及 CRC 核验；“ZIP 目录声明条目数” |
| OFFICE_DOCUMENT_ENTRIES | 当前 Office ZIP 结束目录声明的条目数；“此文档目录声明的内部部件数” |
| OFFICE_ENTRIES | 已遇到的各 Office ZIP 目录声明条目数之和；“Office 目录声明的累计内部部件数” |
| ENTRY_BYTES | 当前目录条目声明的展开大小，可能早于实际解压及 CRC；“目录声明的单条目展开大小” |
| EXPANDED_BYTES | 已遇到的外层及 Office 条目声明展开字节之和；“目录声明的累计展开大小” |
| EXPANSION_RATIO | 当前目录条目声明的展开/压缩字节对；“目录声明的展开倍率” |
| MEMORY_BYTES | 现有预算公式的工作内存估算，含预留及临时空间；“预计工作内存”，不称为进程实测内存 |
| PROCESSING_TIME_MS | 本轮扫描从开始到检查时的已运行毫秒；“已用扫描时间” |

错误状态、详情、失败尝试及释放活动占用在同一拥有者事务提交；保持零 ACCEPTED_ENTRY、零 manifest。读回沿用 owner/project 权限，细节不写入通用事件或日志。刷新、重登、重启和响应丢失后的原批次查询应返回相同事实。

## 4. 存储、历史与页面

- 新增 `V0003` 迁移，允许 `@1/@2/@3` 并保存 nullable JSONB `limit_violation`，数据库约束其形状、计量上限、policy/状态/原因及无 manifest 的关系。`@3` 且 ZIP_LIMIT_EXCEEDED 的 REJECTED 必须有详情；旧记录允许缺省，不回填。现有嵌套拒绝路径约束扩展到 `@2/@3`，旧迁移不修改。
- 已结束的 `@1/@2` receipt、manifest、拒绝、尝试历史及原包保持不变。沿用现有 policy 变化恢复规则：旧活动批次不自动按新 policy 续跑；证明原写者结束后先核对收敛，再由显式放弃释放占用。用户以新批次重新上传，不能通过重试更换 policy 或原字节，不自动重扫旧失败批次。
- MVP API/BFF 仍使用现有只读批次详情接口和鉴权，不添加操作或写入 payload。Web 同步解析可选详情；旧结果仍可读。UI 展示中文种类、数值、上限、适用时的文件位置及整理方法，并保留技术错误码供核对；路径按不可信文本渲染。
- 旧记录仅有代码时显示“资料包超过扫描限制；此历史批次未记录具体超限项”，并引导新批次重传。不得显示实际值为 0，或把新策略宣称为旧批次已通过。
- 部署须采用匹配的 Core、Web 和 V0003。现有测试实例的升级应先检查活动写者和保留数据，沿既有授权边界执行；本提案不授权自动重传真实资料、改写原项目记录、Git 提交/推送或合并。

## 5. 验收与实施范围

一个完整结果覆盖 DocumentDelivery policy/scanner、失败详情事务和 migration、MVP 读取接口与 Web 提示。批准后先更新 MVP01 Spec/Test、共享 MVP API、07 持久化增量及 UI01 Spec/Test 的相应条目，再实施；不复制旧七模块模型、不新增通用配额系统。

1. 外层 1000/1001、单份 Office 1000/1001、累计 Office 20000/20001 的等值与越界测试；跨文档累计，格式失败不返还额度。超过旧合并 1000、仍低于新各上限的正常 DOCX/XLSX 组合可以完成扫描。
2. 原有字节/倍率/路径/CRC/时间/内存及嵌套压缩文件负例保留；每种新超限详情覆盖正确计量依据、数值、上限与路径披露边界，拒绝非法详情。增加“目录声明 1001、真实目录仅 1 条”及伪造展开字节/倍率的反例：允许检查按既有顺序提前拒绝，但详情和 UI 必须使用声明计量措辞，不冒充已经读取或解压的结果。边界按解析路径及固定依据校验，不降低旧防护换通过。
3. 聚焦 HTTP/持久化验证零业务来源/manifest、活动占用释放、授权隔离、刷新与重启读回；旧 @1/@2 历史和活动尝试恢复不被新版本解释。迁移覆盖旧数据升级、全新初始化、再次迁移无操作，保留旧 migration 校验和。
4. 生产构建浏览器验证中文超限提示、历史缺少细节、恶意路径文本、桌面及窄屏；显示的数值必须来自持久详情，不能由前端根据文件名或 ZIP 大小推测。
5. 对这两个真实原包在隔离本地扫描器做只读复测，记录新策略下的扫描状态及逐项限制；不以脱离数据库的扫描结果冒充实际上传或业务验收。若出现其他真实失败，如损坏或不支持格式，应诚实显示，不为本问题顺带放宽。

本设计用 `vibe verify docs --json` 和独立设计审查。实现最终用 `vibe verify full --json`（包含数据库持久化），按项目规则在新或变化的容器环境先执行 `environment`。此前纯 UI 测试豁免不覆盖本轮安全接纳与迁移。真实实例升级、用户重新上传和人工内容验收分别取证；未执行项保持 NOT RUN。
