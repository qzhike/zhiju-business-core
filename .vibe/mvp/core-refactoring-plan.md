## 2. 目标结构与职责

```text
Web UI
  → Core 接口与应用服务
      → PostgreSQL 元数据 + 文件存储
      → 持久化任务与薄执行器
          → 已安装的 CLI Harness + 独立 zhiju-runner
          ← 报告、计划、候选文件、问题与处理结果
      → 接纳版本、人工确认、打包与下载
```

保留现有语言、Web 工程及 PostgreSQL 基础。服务端和后台执行器可属于同一应用，不拆微服务，不建设通用流程引擎或模型推理循环。以下是职责，不是已批准的新目录、Schema 或 API 名称：

| Core 职责 | 最小能力 |
|---|---|
| 项目与资料 | 项目、原始 ZIP、安全解包、目录清单、输入批次、读取限制展示 |
| 分析与范围 | 接纳报告、澄清答复、保存计划和精确范围确认 |
| 文件与讨论 | 不可变 Markdown 版本、阅读与差异、项目/阶段/文件意见、明确人工决定 |
| 阶段与依据 | 质量手册定稿、控制程序与管理制度整体定稿、上游改变后的下游待复核 |
| 执行接入 | 固定输入、单项目单修改批次、真实 CLI 调用、尝试和恢复、结果校验与接纳 |
| 交付 | 精确清单、人工确认、冻结版本、可重试打包和历史下载 |

Core 负责 ZIP/OOXML 包安全和格式接收，内容读取、理解、模板适用性与改稿由独立 Runner 承担。Core 的 Markdown 预览与差异不承诺 DOCX/XLSX 原版式；首次比较显示来源底稿与读取限制，后续 Markdown 版本提供完整文本差异。

## 3. 数据与一致性最小方案

| 数据组 | 必须保存的关系 |
|---|---|
| 项目 | 当前阶段、输入选择、当前确认和待处理事项 |
| 输入批次 | 原 ZIP、条目、相对路径、内容摘要、托管状态；原件不覆盖 |
| 报告与计划 | 所用输入、报告版本、待确认问题、范围确认及其所绑定计划 |
| 讨论与决定 | 项目/阶段/文件版本定位、意见、答复、明确确认的决定；不将普通讨论自动提升为事实 |
| 任务与尝试 | 业务请求、不可变输入快照、当前尝试、执行来源、状态、输出和错误；重试不改写历史尝试 |
| 文件与修订 | 稳定身份、层级、实际 Markdown 文件、前版、来源及所用上游定稿版本 |
| 阶段确认 | 人工确认的精确版本集合；第二阶段将控制程序和管理制度作为一个集合 |
| 交付包 | 人工确认的精确版本清单、摘要、生成状态、实际 ZIP 及历史 |

文件字节为版本依据，解析结构、目录与差异是可重建派生数据。模板、Runner 规则和执行配置只保存本次使用的身份、快照或摘要，不新建模板编辑发布域；凭证和完整模型内部推理不进入业务记录。

需要保留的机制：

- 重复请求识别、预期版本检查和单项目修改任务互斥；阶段确认与交付同时检查版本及待复核状态。
- 外部调用前先保存任务和尝试，返回结果先进入暂存区；文件核对后再提交业务引用。文件存储和数据库的失败边界明确，不假设跨存储原子提交。
- 每份成功文件可独立接纳，但不得因部分文件成功将整个阶段标为完成；涉及跨文件一致性的结果需要联合核对。
- 结果绑定具体尝试、输入、确认范围及上游依据；迟到或过期结果保留历史，不推进当前版本。
- 尚不确定原执行是否结束时禁止盲目重启；期限届满不是外部进程已停止的证明。
- 新上游定稿替代当前依据时，相关下游进入待复核；原阶段确认和旧交付包继续保留。复核形成新的依据与确认记录。

这些机制应落实在少量明确事务和执行状态中，不复制旧 Task/WorkOrder/Context/Completion 多层体系。

## 4. 独立 Runner 接入边界

正式外部目录由用户确认：`/Users/galendai/repo/qzhike/zhiju-runner`；正式模板位于其 `template/`。该目录不属于本次修改范围。用户在 Core 开发期间维护 Runner 的 `AGENTS.md`、Skills 和模板。

Core 只约定集成所必需的输入输出，不要求独立 CLI/TUI 使用依赖 Core 项目、API 或授权对象：

| 方向 | 最小交接内容 |
|---|---|
| 输入 | 分析/生成/修订任务、当前阶段、只读客户资料、Runner 正式模板与规则的固定依据、相关上游定稿、当前候选、意见/答复/明确决定、已确认范围 |
| 输出 | 可展示的报告/计划/问题、实际 Markdown 文件、逐文件状态和限制、所用依据、变化说明；Core 可据此验证身份、文件与范围 |
| 接入层关联 | Core 的项目/任务/尝试身份与外部执行关联、工作目录和恢复信息；不要求 Runner 认识旧 Core Contract |

输出可以由接入层从约定文件组织中提取；是否使用清单文件及精确字段在接入设计中锁定，不预先要求 Runner 兼容完整旧 v0.2/v0.3 平台协议。技术校验不代替语义审阅；改变制度或扩大范围的建议先回到人工的范围确认。

当前只读检查发现 Runner 规则仍有默认 DOCX/Markdown、精确修改文本等旧表述；XLSX 及三阶段行为不能由目录存在推定为可用。这些是用户维护侧的对接事项，Core 不自行修改读取器、生成器、规则或 Skills。正式目录确认也不表示已经完成真实 Harness 调用验证。
