## 1. 目标与开发边界

员工通过 Web UI 完成客户 ZIP 资料上传、分析、修改范围确认、候选审阅、多轮反馈、三个阶段的定稿及最终交付。目标是提高真实项目的交付效率；仅能分析资料或生成个别文件，不构成本闭环完成。

| 边界 | 已确认要求 |
|---|---|
| 客户资料入口 | 必须支持 ZIP 资料包上传，包含首次资料及后续补充批次 |
| 包内输入格式 | 本版全量验收覆盖 bopu 包中的 DOCX、Markdown 及嵌套 RAR 内的文档；嵌套容器不能静默跳过。既有 XLSX 接收契约保留，但该样本不提供 XLSX 业务处理证据；宏不执行 |
| 输出 | Markdown 等文本文件；记录表单先以 Markdown 表格交付，不承诺可执行 Excel 工作簿或 Word 版式 |
| 使用入口 | 内部 Web UI；可逐份预览候选和差异、提交意见、确认阶段与交付包 |
| Core 开发 | 资料托管、ZIP 安全解包、项目过程、意见与版本、人工确认、Runner 接入、恢复和交付 |
| Runner 开发 | 不属于 `zhiju-business-core` 开发范围；用户独立维护其 `AGENTS.md`、Skills、必要工具及正式模板 |
| Runner 独立性 | 脱离 Core，用户仍能通过独立 CLI 执行业务；本版只接通选定的一个 Harness，不同时适配所有工具 |
| 模板与验证 | 真实业务验收使用 Runner 内正式模板；UI 可用明确标注的 mock data 验证交互，不能替代真实内容验收 |
| 现有数据 | 无必须迁移的真实业务数据，无必须兼容的外部接口消费者 |
| 发布基线 | 完整处理用户指定的 bopu 输入文档并交付完整 Markdown 包；小样本不能代替全量验收，不另设 300+ 份数量门槛 |

更新后的 PRD 指定正式 Runner 目录为 `/Users/galendai/repo/qzhike/zhiju-doc-artifacts`，其中 `template/` 是正式模板所在目录。目录身份已确认不等于调用协议、全部输入读取或完整执行已验证。Core 不修改该目录，也不建立另一套模板上传、编辑、发布体系。

## 2. 客户制度与模板的使用原则

1. 首先阅读客户资料，理解其现有制度、文件身份及相互关系，再参考制巨生物模板查缺补漏。
2. 首次分析覆盖四个文件层级；阶段顺序限制生成与定稿，不限制理解客户时的阅读范围。
3. 已有合理且适用的制度应保留。表达、章节组织或编号与模板不同，不直接等于缺口。
4. 对模板内容判断适用性，区分已有覆盖、适用缺口、不适用、资料不足和文件冲突，并提供来源。
5. 未在材料中找到，不等于客户实际没有；模板示例不能成为客户事实。推断、待讨论建议和人工确认决定分别表达。
6. 客户既有质量方针、质量目标、人员架构、组织架构、关联流程和产品流程按业务约定保留。必要变化先说明影响并取得明确授权；普通反馈不能自动授权改变受保护内容。关键内容读取受限时如实报告，不能以生成成功掩盖未读。
7. 客户原件和正式模板只读保留，修改发生在副本或新版本；模板冲突有可见来源、待澄清问题和人工处理入口。

## 3. 三个业务阶段

| 阶段 | 工作内容 | 人工确认与下游依据 |
|---|---|---|
| 质量手册 | 结合整体客户资料和正式模板形成候选，经过多轮讨论与修改 | 确认具体质量手册版本 |
| 控制程序 | 依据已定稿质量手册修订控制程序，核对职责、流程和引用 | 确认控制程序的精确版本集合 |
| 管理制度及记录表单 | 依据已定稿手册和控制程序，修订管理制度并形成关联记录表单，检查整套文件 | 确认本阶段精确版本集合及最终交付清单，下载交付包；不要求为此增加独立页面或通用审批层 |

每阶段都允许讨论和修改。阶段定稿是当前下游依据，允许之后通过新版本重新确认；不能覆盖历史定稿。文件层级有四个，业务工作阶段有三个。

## 4. 从上传到交付的用户操作

1. **建立项目并上传 ZIP。** Core 保存原包，安全解包，保留目录关系并形成文件清单。每个条目显示接收状态；不支持、损坏或受限文件不可静默丢失。后续补充资料形成新批次，不覆盖旧资料。
2. **整体分析与澄清。** Core 调用独立 Runner，使用其正式模板。展示客户制度理解、模板适用性、缺口、冲突、读取限制和待澄清问题。用户可提交意见、答复及补充资料，继续分析。
3. **确认修改范围。** 首次生成候选前必须展示计划，由人确认涉及文件和制度变化。计划解释当前情况、问题、建议及影响，不要求提前逐字确定所有最终文本。
4. **完成质量手册。** 生成候选，逐份预览与对比，保存意见，提交修改，再确认质量手册具体版本。
5. **完成控制程序。** 使用已定稿质量手册及客户资料，审阅、反馈并确认控制程序精确版本集合。
6. **完成管理制度及记录表单。** 使用前两阶段明确的定稿版本，审阅制度与关联表单、提交反馈并修改，确认本阶段内容。
7. **确认并下载交付包。** 展示拟交付文件及精确版本、未解决问题和依据变化；满足条件后由人确认并冻结清单，再生成 ZIP 下载。后续改稿形成新版本或新包，不改变历史包。

初次计划可以覆盖后续阶段。已确认范围内的反馈修改直接执行；新增文件、改变客户制度等扩大范围的操作，先提出新计划并确认。进入下一阶段本身不触发重复范围审批。

## 5. 人工决定、讨论和版本

| 人工动作 | 含义 |
|---|---|
| 范围确认 | 允许修改什么；绑定计划版本和相关资料依据 |
| 阶段定稿 | 哪些精确文件版本可供下游使用；阶段确认绑定该阶段版本集合 |
| 最终交付确认 | 本次交付哪些文件的哪些版本；绑定不可变清单 |

讨论可以针对项目、阶段或文件版本。意见、答复、待确认问题和明确业务决定应保存；页面刷新、离开或服务重启不能丢失已保存内容。针对旧版本的反馈仍保留其原绑定，不能默认为对新版本的确认。

候选生成、技术校验通过、人工定稿和最终交付是不同事实。Runner 不执行人工定稿或交付确认。资料、版本、阶段依据与交付清单不能仅引用可变的“最新版本”。

## 6. 上游改变与必要恢复

上游产生草稿时保留原定稿依据；新版本经人确认替代当前依据后，相关下游标记为“依据已变化，待复核”。Runner 说明哪些内容需要修改、哪些可继续采用及理由。范围内可直接生成修订候选，扩大范围仍先确认。

首版可按阶段保守标记下游，再缩小实际影响范围，不要求逐段落依赖图。复核后重新确认相应版本集合，保留旧依据历史。执行期间上游改变的结果可以留存，但不能自动成为当前定稿；未解决的依据变化阻止最终交付。

| 场景 | 用户可见行为与恢复底线 |
|---|---|
| 上传中断或部分文件不可用 | 保留已托管事实，列明问题，支持补充或重新上传；不显示已完整处理 |
| 重复点击、网络响应丢失 | 查询同一请求的结果，不重复创建执行意图 |
| Runner 失败 | 保留固定输入、原尝试、结果和错误；恢复后建立新的执行尝试 |
| Runner 状态不确定 | 明确显示待确认，先核对原尝试；未确认原执行结束前不盲目启动第二个 |
| 部分文件成功 | 保留已接纳版本，只重试失败部分；有关联影响时形成新版本，不覆盖成功历史 |
| 迟到结果或反馈依据落后 | 保存来源与历史，阻止覆盖当前版本或自动定稿 |
| 服务重启 | 从持久化记录恢复项目、资料、意见、版本和执行状态 |
| 打包失败 | 对同一冻结清单重新打包，不重新生成业务文档 |

同一项目首版只运行一个修改批次；允许查看和保存意见。恢复能力随闭环实现，不把数据丢失、防重复执行和错误版本覆盖问题留到规模优化阶段。

## 7. 验收条件

M1 可先用标明模拟的 mock data 确认页面与操作。真实业务验收以正式 Runner 包内模板为依据；小规模真实验证缩小的是客户样本和任务范围，不能换成自造模板。正式模板中的停用、撤销或不适用内容须按实际状态处理，不因位于正式目录便全部视为适用要求。

每次验证关联实际 Core 修订、Runner 规则与正式模板快照、输入资料和执行结果。用户在开发期间更新 Runner 后，按变化重验受影响部分；不以旧包证据宣称新包已通过。正式包不得被故障注入或验证代码修改。

开发中可先用 bopu 包的少量关联文件验证四层文档和三阶段闭环；发布必须使用用户指定的完整包，包含两个嵌套 RAR 内的文档。固定原包摘要、全部成员清单及处理去向；无法读取或漏处理不能作为完成。真实验收的模板依据始终为正式包。验收应观察：

| 编号 | 可观察的通过条件 |
|---|---|
| MVP-01 | 用户上传 ZIP 后，可核对原包、目录、文件清单及所有受限条目；补充批次可追溯 |
| MVP-02 | 真实 Runner 返回有来源的整体分析、模板适用性与计划；信息不足提出问题，不虚构客户事实 |
| MVP-03 | 未确认计划不生成候选；范围内反馈直接修订，扩大范围重新确认 |
| MVP-04 | 质量手册完成至少一次反馈修改与定稿；Web 可预览真实候选并检查差异 |
| MVP-05 | 控制程序完成反馈与定稿，绑定质量手册版本；之后修订管理制度及关联记录表单，显示前两阶段依据 |
| MVP-06 | 管理制度及记录表单完成审阅，最终整套 Markdown ZIP 内容与人工确认清单一致 |
| MVP-07 | 验证一次上游返工：下游待复核、修订或保留理由、重新确认和交付条件都可观察 |
| MVP-08 | 重复请求、响应丢失、执行失败、重启、部分成功、迟到或依据变化的结果不造成重复执行及历史覆盖 |
| MVP-09 | 合理现有制度得到保留，适用缺口得到补充，跨文件冲突和读取限制可见；人工业务审阅完成 |
| MVP-10 | 对指定完整 bopu 输入落实 MVP-01–09，包含嵌套包中的全部文档，完成处理、审阅和完整 Markdown 包交付；记录耗时、人工操作及主要限制 |

MVP-01–09 是闭环行为要求，可先在小样本验证；MVP-10 是本版完整输入出口。小样本不能代替全量。此前 MVP-10 的“300+”源于 PRD 对典型项目文档量的描述，本版按用户 2026-10-26 的明确决定改为指定输入包验收；更大规模优化后续按实际需要决定。本版全量运行与人工验收仍为 `NOT RUN`，历史证据不因本次修改被否定或扩大。

## 8. 明确移出本次 MVP

- Runner 的代码、`AGENTS.md`、Skills、模板维护与独立 CLI/TUI 体验开发。
- 多用户、多租户、细粒度角色和复杂策略管理；保留必要访问保护和项目/文件归属检查。
- MCP、飞书、企业微信、workbuddy 等渠道以及同时适配多个 Harness。
- Word/Excel 输出、版式还原和可执行电子表格交付。
- 企业长期事实库、完整法规发布体系作为所有项目的前置条件。
- 通用工作流平台、多级质量审批、正式外部发布回执与召回体系。
- 强制 canonical AST/WorkbookSpec 成为唯一内容真相、文档分支合并等超出闭环的能力。

移出范围不取消人工确认、内容真实性、历史保护、依赖检查、幂等、失败恢复或安全边界，也不授权删除旧代码或数据。
