## 已确认的替代关系

| v1 要求 | v2 已确认要求 |
|---|---|
| 项目概览 / 资料 / 处理结果 / 交付四个并列入口 | 当前工作为主入口，全部文件与历史记录为辅助入口；进度和下一步合入工作区顶部，交付在就绪时成为当前任务 |
| 用户先选结果类型、阶段、轮次 | 首次进入自动定位实际可处理任务；主动回看历史时保持选择，提供返回当前任务 |
| 每轮默认展示全部文件 | 当前工作优先展示本阶段需审阅/待处理文件；全部文件一键可查，影响当前推进的跨阶段问题仍显著显示 |
| 详情单独保存，再返回总览汇总提交 | 编辑即保留版本绑定草稿；总览与详情共享本轮操作区，均可核对汇总后提交 |
| 新结果页把生成、答复、恢复和定稿交回旧页面 | 正常动作在同一工作区连续完成；总览/文件详情保留为阅读层级，不形成第二套操作流程 |
| 操作之后由用户进入演练区触发回执或候选 | 正常业务操作驱动完整模拟状态变化；手动回执、故障注入仅用于开发诊断 |
| 累计/本轮差异、精确阶段集合、来源和历史保护 | 保留；首次打开文件仍默认累计变化，整体分析仍覆盖四层，修订和定稿仍分三个业务阶段 |

设计确认只改变后续交互目标，不等于当前页面已实现或 M1-3 已通过。当前工作区聚焦任务不授权排除文件、隐藏阻断、自动批准或迁移旧确认。

  +-- 历史记录：分析、修订、定稿、交付包

当前工作随实际状态连续推进：
  上传资料并开始分析
       |
       +-- 需要澄清 --> 原位答复 / 补资料 --> 继续分析
       |
       +-- 范围可确认 --> 确认范围并生成质量手册初稿
                              |
                    质量手册：审阅 / 反馈 / 新稿 / 定稿
                              |
                    控制程序：审阅 / 反馈 / 新稿 / 定稿
                              |
            管理制度及记录表单：审阅 / 反馈 / 新稿 / 定稿
                              |

准备与交付不是新增修订阶段。阶段定稿后在当前位置提供下一阶段的明确动作，不要求再次找入口或重新确认既定范围。已确认范围内反馈直接修订；扩大范围或新增受保护内容变化仍走对应明确决定。

当前任务由项目事实决定，不能由最近访问页面或最高已有版本推断：先解释影响推进的未决执行/业务阻断，再根据当前阶段有效范围、候选、定稿及上游依据提供可执行动作。主动回看历史不会改变当前任务，也不会自动把阅读切回最新稿。

用户无需先选页面、结果类型和轮次来找任务。当前状态、需要处理的原因、主要操作及操作后的结果相互一致；正常等待、待审阅、失败与业务阻断采用不同表达。“尚未定稿”是正常工作状态，不自动标成错误。

每个状态突出一个主要下一步，相关次要操作仍可用。主操作可随用户工作变化：已记录意见时突出“提交 N 条意见并生成下一稿”，审阅满意时提供完整集合定稿。不得仅因打开过文件就自动推断用户满意或批准。

原概览的三步骤进度在工作区顶部保留；四层统计在全部文件视图可查，不作为完成当前任务的必经页面。窄屏三步骤保持横向，次要说明展开查看。

+-----------------------------------+--------------------------------------+
| 对此文件 / 修改位置的意见                                                |
| [请补充意见________________________________________________________]    |
| 草稿已保留（本次模拟会话）· 绑定此文件 / 第 2 轮 / v2                     |
+--------------------------------------------------------------------------+
| 本轮意见 2 条    [核对意见]    [提交 2 条意见并生成下一稿]                 |
| [上一文件] [下一文件]                              [核对并定稿]          |
+--------------------------------------------------------------------------+
~~~

- 编辑即保留当前项目、阶段或文件精确版本上的草稿，并显示真实保存状态。M1 只声明当前会话内存保留，不新增浏览器持久化或冒充服务器保存。
- 总览与详情使用同一份本轮意见集合和操作区；汇总时展示涉及文件、版本与意见内容。可从任一处核对后提交，不能要求返回另一操作页面，也不能分别生成两个修改意图。
- 编辑草稿不等于提交；提交成功也不等于新稿已生成或阶段已定稿。按钮需驱动正常模拟修改到新候选可查看，处理中有清楚状态，不要求用户手工投递模拟回执。
- 来新稿只提示并提供明确查看入口，不替换当前阅读、草稿或旧确认。返回文件清单恢复原筛选、选择和滚动；旧意见不能静默迁移到新版本。
- 有未提交草稿时，定稿前提醒并让用户明确处理；不能静默忽略草稿，也不能把保存草稿当作新增业务审批关卡。
- 定稿在当前工作区核对完整精确版本集合及上游依据，不进入另一套阶段审阅 UI，不逐文件批准，不允许取消必需成员绕过完整性。第三阶段定稿与最终交付确认仍是不同决定。
- 目录及意见区按需展开，避免固定四栏挤压正文；共享操作区在需要时始终可达。窄屏使用统一差异或原文/修订切换，保留意见、版本、来源和返回；宽表只在阅读区域内部滚动。

| 比较方式 | 左侧 | 右侧 |
|---|---|---|
| 累计变化（首次默认） | 文件初始底稿 | 所选轮次精确候选 |
| 本轮变化 | 上一轮精确稿件；首轮明确使用实际输入底稿 | 本轮精确稿件，沿用时可为相同版本 |

DOCX 显示可追溯提取正文并保留限制，不宣称还原 Word 排版，不把规范化文本索引冒充原始物理行号。

## 完整文件与历史视图

“全部文件”保留全部批次、目录、容器及成员，并支持本阶段、本轮涉及、待处理筛选。当前任务视图只调整展示重点，不改变接收成员、处理范围或上传数量。上传成员、容器、预期待补项和已确认新增分别统计；读取状态、本轮处理结果和人工定稿分别表达。

| 状态 | 必须保持的显示和行为 |
|---|---|
| 分析或计划阶段，尚无候选 | 展示原文、发现、拟议动作及“尚未生成候选”，不制造修订稿 |
| 已确认新增，无客户原件 | 左侧明确无原件，右侧只展示实际候选 |
| 沿用 | 展示沿用的精确版本与理由，不制造新版本 |
| 已知失败或范围内缺输出 | 文件仍可查；显示失败或未返回结果；上一稿不能冒充本轮产物 |
| 原件不可读 | 显示读取限制及补充入口，不伪造原文 |
| 预期待补项 | 显示来源、适用性与待确认事项；包中未找到不等于客户没有 |
| 后来补充或未纳入所选轮次 | 原件仍可查，明确未纳入该轮，不改写该轮输入、结果及统计 |
| 上游重新定稿 | 展示旧/新依据及影响，当前任务提供复核；旧结果和定稿留在历史 |

历史视图展示固定轮次、尝试、意见、定稿与包。主动选择历史时保持阅读，并明确区分“正在查看的历史”与“项目当前任务”，提供返回当前任务入口；已替代计划不能重新提交。失败重试或后续成功不删除原尝试及详情身份。

## 状态与主要操作

| 当前状态 | 用户应理解的事实 | 主要操作 |
|---|---|---|
| 尚未上传 | 需要哪些资料 | 上传资料并开始分析 |
| 待澄清 | 缺什么，为什么影响当前工作 | 提交答复并继续分析 / 补充资料 |
| 范围待确认 | 涉及文件、制度变化和影响 | 确认范围并生成质量手册初稿 |
| 正在处理 | 系统正在做什么，暂时无需用户推进 | 显示进度和等待原因；查看资料为次要操作 |
| 候选可审阅 | 本轮改了什么，需要核对什么 | 审阅本轮文件 |
| 有未提交意见 | 意见数量、对象与版本 | 核对汇总并提交下一轮修改 |
| 阶段可定稿 | 将确认哪个完整版本集合 | 核对并定稿；随后明确下一阶段动作 |
| 已知部分失败 | 哪些保留、哪些失败 | 重试失败部分 |
| UNKNOWN | 原执行结果尚未确定 | 核对执行状态 |
| 交付就绪 | 本次交付的文件与精确版本 | 确认交付清单并生成文档包 |
| 包可用 | 包的清单、版本和时间 | 下载文档包 |

实际阻断优先解释，不能仅因有意见草稿或未定稿就渲染错误。所有状态的正常路径使用业务文案；保留一个持续可见的模拟/刷新限制提示，诊断标识、故障注入和手动回执放入开发区，不作为普通用户完成旅程的前置。

## 当前工作文件浏览器设计（2026-10-30）

状态：**IMPLEMENTED / AUTOMATED VERIFIED / HUMAN VISUAL ACCEPTANCE NOT RUN**。根据用户修订意见，“当前工作”页把左侧项目文件区扩大为桌面主工作区的 50%，采用传统文件浏览器的详情列表，并为每份文件展示最后修改时间与修改人。本节给出补充字段与交互建议；不声明已经实现。验收范围为“当前工作”，复用现有项目目录及其身份/视图状态，其他页面不因此统一改成 50:50。

### 50:50 布局与浏览器式列表

- 桌面主工作区扣除外边距及列间距后，两列等宽：左侧项目文件，右侧当前任务、阅读和意见。50% 指可用内容宽度，不是整个浏览器窗口宽度；不继续沿用当前固定 288px 窄栏。至少在 1280×800、1440×900、1920×1080 验收等宽与可读性。
- 左右区独立滚动，文件区的类型切换、搜索/筛选和列表表头固定。全局页头不挤进任一列；Mock 控制继续使用独立悬浮面板。
- 左侧采用**有目录层级的详情列表**：文件夹/文件类型图标、缩进、展开箭头、对齐字段、明确选中行。保留“客户原始文档 / 修订文档”两视图；原件按批次和原路径，修订按四类文档组织，分组不伪装为实际文件路径。不再以一文件一卡片或大段说明堆叠清单。

- 文件信息按选中行在左侧底部展开，正文仍在右侧。当前阶段任务、阅读版本、意见草稿与目录选择分开；排序、搜索、目录展开及类型切换不改写任务或已打开的精确版本。每个类型在当前项目会话保留搜索/筛选、排序、展开和列表位置；已有刷新/失权清理规则保持。

| 字段 | 默认呈现 | 含义与边界 |
|---|---|---|
| 文件名 / 目录 | 主列，含类型图标、层级与选中态 | 长名称可换行；已有文档编号可作次要信息；同名文件可从路径/批次区分 |

| 最后修改时间 | 固定字段；窄屏行内显示 | 该行所代表文件/精确版本的最后内容修改时间，绝对日期和时间；显示时区，详情保留来源与原始精度 |

### 修改信息的真实性

1. **客户原始文档**：只有取得该文件自己的修改元数据才填写修改时间/修改人；文件记录中的作者标明“文件记录”，不能当作平台核验身份。“作者”若只是初始作者、不是最后修改者，不填入修改人。上传时间、上传人另列，不替代修改记录；容器的时间/作者不传给内部所有成员。
2. **修订文档**：修改信息绑定该行所示精确版本，使用实际内容修订/生成记录。AI 生成的新版本显示“AI 生成”或已有具体来源；发起意见者单独显示，不自动成为修改人。仅提交意见、批准或定稿而内容未变，不更新最后内容修改时间/修改人。修改人字段可用 AI/系统主体，但不宣称真实 Runner 已接通。
3. **缺失仍可见**：每个文件行都有这两个字段；未提供显示“未提供”，无权限显示“无权查看”，读取失败显示“读取失败”。真实目录等非文件节点标“不适用”；归档容器作为文件有自己的修改字段，虚拟分组不编造修改人。
4. **时间及排序**：完整时间显示为 `YYYY-MM-DD HH:mm`，列表统一声明显示时区；有偏移量的来源转换为该时区，原值在详情可查。来源只有日期就只显示日期，无时区则标明“时区未提供”，不补造小时/时区。没有可比较时间的项排在有效时间之后，不当作最新或纪元时间；相同值保持稳定顺序。
5. **历史与更新**：列表显示哪一精确版本，修改信息就属于哪一版本。阅读旧版本时明确区分“正在阅读 v2 / 列表当前 v3”；新候选不静默替换读者或草稿。新数据到达保留选中行、焦点和可见位置，不能重绑版本或把另一个项目的数据回填。
6. **当前数据缺口**：现有 `OriginalRow` / `RevisionVersion` 展示模型未提供完整修改时间和主体；`InputBatch.submittedAt` 仅为批次提交时间。M1 可补合成、可复现且绑定版本的元数据样例，同时保留缺失/受限反例；真实来源缺失时如实显示，不能据此新增或假定 Core/Runner 公开字段。真实元数据接入须随其 owning 能力单独核实。
