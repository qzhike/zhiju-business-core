## 目标与完成基线

员工通过 Web 完成资料上传、分析与澄清、修订范围确认、三阶段审阅、多轮反馈，最终下载完整 Markdown 文档包。**先定稿可完整操作的 mock Web UI，再按用户流程接通真实 API 和业务能力。**

本版必须完整处理用户确认的 **bopu 输入文档集合**。2026-11-03 用户取消嵌套 RAR 处理，改为上传 ZIP 时检测内层压缩文件并整包拒绝；成功上传及发布验收使用用户整理后不含嵌套压缩文件的 ZIP，重新固定摘要与清单。小样本和 mock 只用于开发验证，不能代替发布验收；不再把抽象的“300+ 份”另设为本版数量门槛。新上传规则的产品决定已确认，已批准技术方案及交付边界见 [嵌套压缩文件拒绝设计](../decisions/mvp-nested-archive-rejection.md)。

- 历史原包只读清点：外层 55 份 DOCX、36 份 Markdown、2 个 RAR；RAR 内另有 85 份 DOCX，共 176 份文档条目。这仅是旧容器目录统计，不再作为新规则下的成功上传或嵌套功能验收要求；原包保留为拒绝反例，不修改或自动展开。
- 旧输入路径与原 ZIP 摘要固定在 `.local/mvp/mvp-v1-release-input.json`（Git 已忽略，仅含元数据）。用户整理后重新确认新输入基线，不能覆盖旧证据或直接沿用旧数量。首次真实业务验收固定新的普通文档清单、正式模板快照及 Runner/Core 修订。客户路径、正文和详细清单留在本地受控证据中，不复制进公共开发文档。
- “完整处理”指全部输入可核对、可读取并进入分析与范围判断；需要修改的文件形成完整候选，沿用或不适用的文件有依据和人工判断。无法读取、遗漏或未解决的处理失败不能以排除条目通过验收。
- 三阶段按更新后的 PRD：**质量手册 → 控制程序 → 管理制度及记录表单**。产品细则见 [可用闭环](usable-loop.md)，已有旧 UI 行为不等于新顺序已实现。
- 非目标：多租户、复杂权限平台、MCP/外部聊天渠道、Word/Excel 输出、通用工作流平台。必要访问保护、持久化、原件保护、版本正确性和失败恢复随功能交付。

## 里程碑

| 顺序 | 用户得到的结果 | 进入条件 | 完成时怎么验收 |
|---|---|---|---|
| M1 · Web UI 定稿 | 同一项目内用 mock data 从首页走到文档包下载，能够处理反馈、冲突、返工和失败 | 当前可开始；复用现有 Web 与 U1–U3 演练基础 | 人类完整试走并确认流程；明确标注模拟状态与模拟产物 |
| M2 · 真实质量手册闭环 | 真实资料可读、分析可审、意见可保存，质量手册完成一轮修改并定稿 | M1 人工确认；本段所需 Runner 能力与最小接入设计核对完成 | 用 bopu 包的关联子集接通真实链；同时证明完整包的接收与读取清单无遗漏 |
| M3 · 完整业务与文档包 | 按三阶段完成整套修订，下载与确认清单一致的 Markdown ZIP | M2 完成 | 真实关联样本贯穿三阶段，返工、重试、重启及下载均有证据 |
| M4 · bopu 全量验收与发布准备 | 完整 bopu 输入处理完成，人类可审核并取得整套可交付文档 | M3 完成，完整输入和正式模板快照固定 | 全量内容与包清单通过人工验收，约定内部运行环境验证完成，再由用户决定发布 |

不按前端、API、数据库分成互相脱节的里程碑。M2 起每项工作连同入口、保存、结果与必要恢复一起完成；未来阶段只保留出口，不提前展开大型 backlog。

## 跟踪与证据规则

- 人类负责业务规则、冲突处理及 UI/内容/发布确认；Agent 负责实现、测试、整理证据和更新上述 checklist。每次交接说明完成的 ID、对应修订与证据、当前阻塞、下一个 ID。
- 证据使用四类：**真实运行有证据 / 合成或 mock 验证通过 / 仅静态实现存在 / 未知或受阻**。记录输入标识、执行方式、结果及 Core/Runner/模板版本；人工结论单独记录。
- 本文件按用户要求承载 release checklist；[roadmap](../product/roadmap.md)只保留方向，不重复任务状态。已有 Issue/PR 保存详细执行和验收证据；尚未授权创建时，使用本地受控证据定位，不为跟踪新建平台或大量日志文档。
- 每次只细化当前可执行项；进入真实接入前同步受影响的 owning Spec/Test，按既有规则完成必要设计与审查。UI 定稿不直接批准新 API、数据库或 Runner 协议。
- 验证继续使用 [既有验证基准](../high-level-docs/08-verification-baseline.md)。文档整理使用 `docs`；后续 UI/业务工作按实际差异和已确认的交付阶段选配置目标，本计划不降低工程检查或改写 CI 路由。
