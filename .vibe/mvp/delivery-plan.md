# MVP 交付计划：先订正 UI，再补齐业务闭环

日期：2026-10-20

状态：`DELIVERY PLAN USER CONFIRMED / UI FLOW ACCEPTANCE NOT RUN / BACKEND DESIGN PENDING`

用户已于 2026-10-20 确认本交付计划：优先订正 UI，确认完整操作流程后，再补齐后端业务能力。本文细化这一顺序、交付结果、依赖和验收；计划确认不表示 UI 流程已经验收、业务已经实施或字段级技术设计已经批准。

产品要求唯一见 [MVP 可用闭环](usable-loop.md)，架构取舍及代码处置见 [Core 缩编重构方案](core-refactoring-plan.md)，Current/Next/Later 唯一由 [roadmap](../product/roadmap.md)维护。本文不维护任务状态、Issue 正文或逐轮执行日志，也不改变既有契约、数据库及验证门禁。

## 1. 交付路径与完成口径

```text
订正现有 UI，并形成可连续试走的三阶段流程
  → 用户确认页面操作、确认对象与返工路径
  → 根据确认后的流程完成最小后端设计和 Runner 对接核验
  → 按用户结果逐段接入真实服务
  → 正式模板下的小规模真实闭环（MVP-01–09）
  → 300 份以上资料及效率验收（MVP-10）
```

先做 UI 不等于先完成所有视觉打磨。首轮确定员工从哪里进入、看什么依据、提交什么意见、确认哪些版本、失败后如何继续；字号、间距等可逆细节可随使用修正。后端按已确认旅程补齐，不先把旧七模块全部重构完。

| 交付节点 | 用户可以得到什么 | 进入下一节点的条件 |
|---|---|---|
| UI 流程确认 | 在同一项目中连续试走上传、分析、范围、三阶段审阅、返工和交付 | §3 的试走场景通过，用户明确确认本轮流程；真实业务仍未验收 |
| 后端开工准备 | 能审查每个按钮的服务端职责、保存内容、失败行为及 Runner 交接 | §4 的关键设计和外部依赖闭合，完成适用的 T2 独立审查与人类技术批准 |
| 小规模可用交付 | 使用真实客户 ZIP 和正式 Runner，从上传走到可下载的精确交付包 | MVP-01–09 全部有对应真实运行和人工业务证据 |
| 完整 MVP | 同一流程处理 300 份以上实际资料，能比较实际工作效率 | MVP-10 完成；规模、内容质量、人工使用证据齐全 |

本轮仅交付规划文档。后续 UI 实现、后端实现、Issue 发布、Git 提交、推送和合并按各自授权推进；旧代码删除、旧环境清理及 Runner 修改不由本计划授权。

## 3. 第一阶段：UI 订正与流程确认

### 3.1 交付边界

在现有 Web 工程及环境 A 中完成；复用共享页面和隔离开发 adapter，不建设第二套一次性原型站点。可以模拟返回、保存和失败状态来检验交互，但必须持续标明演示性质，不能调用未批准的生产写接口或把模拟回执显示成真实业务事实。

本阶段的页面字段是待确认的展示模型，不提前冻结 API 名称、数据库表或 Runner 协议。生产入口仍根据实际能力显示可用性；模拟流程通过不使生产按钮自动可用。

UI 内容与业务演练也遵守正式模板约束：

- 从 `/Users/galendai/repo/qzhike/zhiju-runner/template/` 只读选取四层正式模板作为内容依据，保留来源及快照标识；不复制维护第二套模板，不以旧匿名 fixture 的业务内容替代新 MVP 验收。
- 客户事实来自可合法用于验证的客户样本；未提供时明确缺资料，不把模板示例当客户事实。可以先完成导航和通用状态交互，但相关业务内容试走仍为 `NOT RUN`。
- 先沿用一组约 5–10 份有关联文件完成所有页面的连续试走；UI 的状态模拟与后续真实 Runner 输出分开标识。

### 3.2 页面与操作订正清单

| 工作面 | 订正后的操作与显示 | 必须避免的误解 |
|---|---|---|
| 工作台与项目概览 | 展示当前业务阶段、待我处理、最近结果及下一动作；能回到资料、计划、当前审阅及历史 | 三阶段与四层文件分别表达；不按旧模块组织主流程，不靠合成百分比表示完成 |
| 新建项目与资料 | 沿用简洁客户/项目入口；首次 ZIP 和补充批次可区分；列出目录、DOCX/MD/XLSX 条目、受限原因和下一动作 | 接收不等于读完或分析成功；XLS 转换和 PDF 不支持须可见，失败条目不消失 |
| 分析与澄清 | 展示客户制度理解、来源、已有覆盖、适用缺口、不适用、冲突与资料不足；可答复、补资料、查看分析版本 | 正式模板不是默认全适用要求；待确认建议与已确认决定分开 |
| 修改计划与范围确认 | 说明当前情况、问题、建议、影响及涉及文件；确认精确计划与资料依据；保留既有确认和新范围差异 | 范围内反馈不重复审批；新增文件或制度变化先确认新计划；旧计划不能自动确认新版 |
| 三阶段审阅与意见 | 固定当前阶段、文件版本和上游依据；阅读/差异/唯一意见区协同；明确意见作用于项目、阶段或文件版本 | 四层文件不变成四个串行审批阶段；第二阶段可联动改两类文件，整体确认一个版本集合 |
| 阶段定稿 | 第一次确认质量手册版本；第二次确认控制程序与管理制度集合；第三阶段审阅记录表单并走最终交付确认 | 不额外增加记录表单定稿关卡或逐文件正式批准要求；阅读、候选到达不触发定稿 |
| 执行与恢复 | 单项目单修改批次，执行时仍可查看和保存意见；区分等待、处理中、部分成功、失败、待核验和结果可审阅 | 状态未知先核对原尝试，不出现可重复启动的普通重试按钮；新候选不抢走当前阅读版本 |
| 上游返工 | 上游草稿不改变当前依据；新定稿替代依据后显示下游待复核、受影响范围及修改/保留理由 | 不自动抹掉下游成果或历史确认；依据未解决时阻止最终交付 |
| 最终交付与历史 | 展示文件及精确版本、未解决问题、依据变化；明确确认后冻结，再显示打包、重试和下载 | 打包失败重试同一清单；下载响应不代表客户已收到；新改稿不覆盖旧包 |

### 3.3 UI 实施顺序

以下是三个可连续评审的体验结果；每批包含对应页面、展示模型、隔离 adapter 和必要浏览器场景，不按“页面/样式/测试”分成独立交付目标。仅当前批次进入 Issue 准备，后续批次按前一轮试走反馈细化。

| 批次 | 完整结果 | 范围与出口 |
|---|---|---|
| U1：从资料到确认范围 | 用户能理解“收到了什么、分析发现了什么、将改什么”，试走到一次明确范围确认 | 订正工作台/项目导航、资料批次、分析澄清和范围页；能返回补充资料；同时演练范围内修改无需再确认和扩大范围需新确认。不接真实业务 API |
| U2：三阶段审阅与定稿 | 用户知道当前在改什么、意见属于哪版，以及本次定稿给下游提供什么 | 复用审阅区，接上质量手册、控制程序/管理制度联动及记录表单；演练一次反馈后新候选、一次第二阶段整体确认；刷新/保存状态按模拟边界说明 |
| U3：返工、恢复与交付 | 用户能从头走到最终包，并看懂返工或失败时的下一动作 | 将上游返工、部分成功、未知执行、打包失败与历史包纳入同一旅程；补齐 U1/U2 的联动缺口，完成全链路试走 |

每批先给用户可操作页面，再处理会妨碍任务完成的反馈。局部页面认可不等于整体流程确认；U3 结束后再作一次从头到尾的确认，避免后端依据互相矛盾的页面实现。

### 3.4 UI 流程确认场景

所有场景均在同一项目与连续版本关系中试走，不用互不关联的页面截图代替。

| 编号 | 用户必须能观察到的结果 |
|---|---|
| UI-01 | 首次 ZIP 和补充批次、三种输入格式与受限条目可核对；从分析问题可回到对应资料 |
| UI-02 | 能区分来源事实、缺口建议与待澄清问题；答复后可查看新报告，旧报告与意见保持原绑定 |
| UI-03 | 未确认范围不能进入候选生成；范围内反馈直接修改，扩大范围需确认；进入下一阶段不重复确认范围 |
| UI-04 | 质量手册经过一次反馈、差异查看和精确版本定稿；新候选不会替换正在阅读的版本或丢失意见 |
| UI-05 | 控制程序和管理制度在同一阶段联动修改并整体定稿；记录表单能看到前两阶段的精确依据 |
| UI-06 | 上游仅有新草稿时旧依据仍有效；新定稿后下游待复核、理由和重新确认入口可见，未解决时交付被阻止 |
| UI-07 | 重复点击、响应丢失、部分成功、失败和执行未知有明确下一动作；已保存、未保存、保存失败与模拟状态可以区分 |
| UI-08 | 最终确认对象是精确文件清单；打包失败可重试原清单，历史包不变；用户能回到项目继续查看 |

退出条件：

1. UI-01–08 均有实际页面试走证据，用户能说清三类确认的区别，并明确确认整条流程。
2. 关键入口、主操作、确认对象、必要失败与返回路径已确定；没有需要后端实施者猜测的业务步骤。
3. 已将确认后的页面行为和验收场景归入 owning UI Spec/Test；Issue/PR 记录确认的修订、页面证据、剩余限制，本文不另设确认日志。
4. 只声明 UI 流程通过；真实保存、Runner、重启恢复及业务内容有效性继续按各自证据验收。

## 4. 第二阶段：从确认的 UI 反推最小后端设计

UI 确认之后才固化新业务 API、状态与持久化模型并开始后端实现。UI 阶段允许只读核对 Runner 和现有能力、暴露不可实现的假设，不提前建设后端框架。

该阶段整体为 T2。使用缩编方案已有职责划分，围绕已确认页面收拢以下设计，不重新编制全平台设计包。

| 设计主题 | 必须形成的可审查结论 | 对应权威落点 |
|---|---|---|
| 页面动作与服务端结果 | 每个查询/命令唯一所有者，输入依据、预期版本、回执、错误及权限；明确读取、保存意见、提交执行和人工确认的区别 | 共享 API 与 owning Module Spec/Test；公开名称登记到 06 |
| 最小数据与文件关系 | 项目、输入批次、报告/计划、意见/决定、文件版本、阶段确认、尝试及交付包；不可变身份、摘要、归属和事务边界 | 02/04/05/07 的受影响定义及 owning Spec/Test；新所有权不能靠目录名推断 |
| 固定输入与 Runner 接入 | 选定一个实际 Harness；核对启动、工作目录、输入物化、输出提取、关联和状态核对；覆盖 DOCX/MD/XLSX 与三阶段 | Runtime 接入契约及测试；Runner 内容由用户维护，Core 只做薄接入 |
| 反馈、定稿和依据变化 | 范围内修改/扩大范围分流、第二阶段整体确认、上游草稿与新定稿区别、旧结果接纳/隔离和交付阻断 | owning 业务 Spec/Test，与 UI 已确认语义逐项对照 |
| 安全与必要恢复 | 最小登录方案、项目/文件归属、ZIP/OOXML 限制、服务重启、未知执行核对、部分失败、文件暂存/引用提交及打包恢复 | 02/05/07、安全基线与 owning 失败场景 |
| 初始化与联调 | 精简主链的新入口和独立数据边界，复用可用 macOS 环境能力；选定实际存储，保留旧环境及回退方式 | macOS runbook、适用部署/安全基线及启动器设计 |

设计出口不是“所有文档写完”，而是下一真实用户结果需要的关键语义可执行、可验证：

- 每个确认按钮都有精确对象与服务端验证；前端禁用不能代替后端约束。
- 输入、版本、意见和尝试可持久恢复；未知执行、并发确认、部分成功及迟到结果的处理无空白。
- 用正式包完成一次有限的 Runner 对接核验，确认所选 Harness 的输入输出组织和三种输入格式读取边界。不能从目录存在推导能力已具备；能力缺口交由用户维护 Runner。
- 正式模板快照、合法客户样本、实际执行配置可供下一批使用；凭证不写入文档或业务记录。
- 相关 Spec Delta 完成独立审查和适用的人类技术批准；之后才将对应后端实现评为 NOW + READY。

同一组设计可按下一交付结果逐步闭合。资料接收的独立结果不必等待所有 Runner 生成能力完成，但不得把缺 Runner 的后续批次标为 READY；跨版本、确认与恢复这些难以补救的基础语义不能留到最后。

## 5. 第三阶段：逐段接通真实业务能力

每批交付都从已确认 UI 进入，包含必要接口、持久化、文件存储、接入和浏览器读回。组件完成不等于用户结果完成。以下 B1–B5 是依赖有序的交付候选，只在前置满足时准备当前批次；小规模 MVP 的完整出口仍是 B5 之后的 MVP-01–09。

| 批次 | 用户得到的完整结果 | 前置 | 必须随批完成的验收与恢复 |
|---|---|---|---|
| B1：项目与资料托管 | 登录后建项目，上传真实 ZIP，核对原包、条目及补充批次，重启后仍能找到 | 入口保护、数据/存储、ZIP 安全及三种格式接收设计已批准 | 覆盖 MVP-01；损坏/不支持/受限条目可见；中断与同请求恢复不重复建批次；归属检查及文件/数据库失败边界有证据。未接分析时明确等待 |
| B2：整体分析与范围确认 | 提交真实分析，收到带来源的报告和计划，可答复/补资料再分析并确认修改范围 | B1；真实 Harness、正式模板和分析交接核验通过 | 覆盖 MVP-02 及 MVP-03 的前置确认；固定输入、持久尝试、原请求查询、未知状态核对、报告/计划版本与意见保存。此批不宣称生成可用 |
| B3：质量手册完整修订 | 生成真实候选，查看差异，保存意见，提交至少一轮修改并定稿精确版本 | B2；文件版本/反馈/范围变更/定稿设计与 Runner 生成能力就绪 | 覆盖 MVP-03/04；未确认范围拒绝生成，范围内修订无重复审批，扩大范围须新确认；旧反馈不改绑，响应丢失不重复执行，服务重启不丢已保存内容 |
| B4：第二阶段联动与记录表单 | 按定稿质量手册联动修订控制程序和管理制度，整体定稿后生成记录表单 | B3；集合确认、跨阶段依据和联动结果接纳设计就绪 | 覆盖 MVP-05 及 MVP-06 的表单生成；至少一次联动修改；部分成功保留但不冒充阶段完成；执行中依据变化不让旧结果推进当前定稿；此批即验证 MVP-07 的上游返工 |
| B5：精确交付与闭环验收 | 检查记录表单与全套文件，确认精确清单，取得匹配的 ZIP，并能查看历史包 | B4；不可变清单、内容核对、打包及下载设计就绪 | 完成 MVP-06/07，汇合各批 MVP-08 恢复证据及 MVP-09 人工内容审阅；打包失败只重打原清单；未解决依据变化阻交付；包内字节/文件集合与确认相符 |

幂等、归属、历史保护及恢复在首次引入相应能力时完成，不安排一个“最后统一补可靠性”的批次。尤其是 B2 的外部调用必须先保存任务/尝试，再执行；B3 的意见持久化必须先于宣称“已保存”；B4 的上游替换必须与下游待复核一致；B5 不能在下载时临时读取可变的“最新版本”。

每批接线后回到同一 UI 旅程核对实际结果。如果真实能力迫使主流程、人工确认对象或业务语义改变，先更新并确认受影响的流程，再继续依赖实现；普通接口映射和布局微调不要求重做整轮产品确认。

## 6. 第四阶段：实际规模与效率

只有小规模 MVP-01–09 通过，才进入 MVP-10。该阶段保持同一业务流程和正式模板基准，以 300 份以上实际客户资料完成处理、审阅、返工和最终交付。

| 检查面 | 验收观察 |
|---|---|
| 完整性与资源 | ZIP/OOXML 数量与大小预算覆盖真实资料；清单无静默遗漏，读取限制可定位；执行可分批但依据不漂移 |
| 工作区可用性 | 300 份以上文件的查找、筛选、版本/差异查看与批次确认可完成，不要求用户逐页重复录入同一信息 |
| 联动与恢复 | 实际跨文件冲突和上游返工可处理；失败部分可恢复，已接纳成果和历史不覆盖 |
| 业务质量 | 保留合理客户制度、补齐适用缺口，待确认事项与正式决定清楚；正式模板中的停用/撤销内容不被误用 |
| 效率 | 在可比任务上记录总耗时、人工操作耗时、重复操作及返工次数，与现行工作方式比较 |

产品已要求效率比较，但未确定提速百分比或固定时延。先取得可比基线并与用户约定可接受结果，不编造数字作为已确认指标；不能仅凭 300 文件处理完成就宣称效率改善。优化只针对实测瓶颈，不引入第二种 Harness、通用调度平台或全量细粒度依赖图。

新链路替代成立后再单独评估旧实现退出。依赖、启动、数据和测试用途清点完成并取得相应授权前，保留旧模块、旧环境和历史证据；清理不占用 UI 订正的关键顺序。

## 7. 验证与证据安排

### 7.1 配置目标

| 变更 | 验证安排 |
|---|---|
| 本计划及严格文档变更 | `vibe verify docs --json`，另检查引用和计划的一致性 |
| UI 订正 | 仅完整 PR diff 落在 [现有低风险允许列表](../../tools/verification/select-target.mts)时用 `vibe verify code --json`；新页面、审阅/执行/交付及真实导航接线等允许列表外路径默认 `full`，不因“先做 UI”豁免 |
| Core/API/持久化/Runner 接入/安全/初始化及依赖变更 | `vibe verify full --json`；新或实质变化的容器环境先执行一次 `vibe verify environment --json`，有效成功结果可复用 |
| 真实业务与规模验收 | 在适用配置检查之外，使用正式模板、真实 Harness 和实际客户样本执行对应 MVP 场景，独立记录人工判断 |

遵守 [验证基准 §2.1.1](../high-level-docs/08-verification-baseline.md#211-配置化验证目标与-ci-路由)及 [§2.9](../high-level-docs/08-verification-baseline.md#29-缩编-mvp-正式模板与闭环验收)。不把新 UI 路径自行加入低风险列表来缩短检查，也不重复运行已有可信、同修订、同范围的配置验证。

### 7.2 分层证据

1. **页面证据**：环境 A 的真实浏览器交互与用户流程确认，只证明页面行为。
2. **业务技术证据**：实际 Web/BFF/Core/数据库/文件存储的读写、重启与必要失败测试，只覆盖已接入能力。
3. **Runner 证据**：实际 Harness、规则/模板快照、输入及输出，与 Core 接纳结果关联；受控模拟不代替真实调用。
4. **人工业务证据**：客户制度保留、适用性、跨文件一致性及交付内容由人审阅；自动化成功不代替。
5. **规模效率证据**：300 份以上资料、可比基线和实际使用结果；不由小样本外推。

每次业务验收绑定 Core 修订、Runner 规则/正式模板快照、客户输入及实际结果。正式 Runner 包只读；故障输入从正式基准可追溯派生，用户更新 Runner 后重验受影响范围。执行证据与流程确认记录进入对应 Issue/PR，未运行部分保持 `NOT RUN`；有 PR 时按项目要求保存正式 Review。

## 8. 依赖、责任与启动安排

| 事项 | 责任 | 最晚需要的节点 | 未满足时的处理 |
|---|---|---|---|
| 页面操作与整条流程确认 | 用户作产品决定，Planner/Implementer 提供可操作结果 | U1–U3 局部反馈及 UI 总体验收 | 后端新业务设计不冻结，继续修正受影响 UI |
| 正式模板内容和合法客户样本 | 用户提供/确认可用范围，实施者只读准备 | 涉及业务内容的 UI 试走；真实 B1–B5 验收前具备四层/三格式样本 | 导航与状态订正可继续，业务内容及真实验收不能冒充通过 |
| Runner 规则、XLSX/三阶段能力、正式模板 | 用户维护 Runner；Core 实施者核验交接 | 对应 B2–B4 批次准备前 | 缺口明确回交 Runner 维护侧，不在 Core 偷补一套业务 Agent |
| 单一 Harness、最小登录、存储和新数据边界 | Planner 提出最小技术选择，用户完成适用的人类技术批准 | 对应后端 T2 设计出口 | 只阻塞依赖该选择的真实实现，不阻塞 UI 订正 |
| 独立审查与精确修订证据 | Reviewer、Implementer，必要时人类技术审查者 | 各交付合并前；T2 设计批准先于实现 | 修复实际阻断，按最新 head 复核；保留未运行边界 |
| Issue/Git/合并与清理 | 用户授权，执行者按门禁交付 | 各操作发生前 | 规划完成不自动产生发布、合并或删除权限 |

下一轮依据 U1/U2 的实际反馈准备 U3，核对当前 main 的上游依据、正式内容来源、owning UI Spec/Test 增量及 NOW + READY，再按授权创建并实施当前批次。每批以“可操作结果 → 用户反馈 → 修正 → 适用验证”推进；完整流程确认后再转入 §4。当前没有人员投入与 Runner 就绪日期，不承诺日历工期；UI 确认后结合真实对接结果估算当前后端批次，不一次性排死整个重构。
